## 一、项目概述

《红颜局中局》是一档在抖音平台运营的直播选秀节目。本小程序是节目的**直播伴随工具**,核心功能:

- 观众查看选手信息与实时人气数据
- 观众通过卡密核销获得数字权益(选手数字写真)并为选手助力
- 节目组通过场控后台管理直播互动环节、积分与赛程
- 观众在投票日参与"真相识破"互动(节目核心观众参与环节)

系统于 2026 年 6 月 23 日正式上线,以"轮次"为周期持续运营。

## 三、代码与文档现状(对接手方友好程度)

本项目从首行代码起即按"可移交第三方维护"标准建设:

1. **架构文档完整**:有唯一权威的《开发指导手册》,含模块划分、接口契约、数据库 Schema。
2. **代码注释规范**:public 方法均有 Javadoc;复杂逻辑(积分计算、并发控制)有行内注释;业务常量集中管理并附含义。
3. **单元测试**:核心模块(积分引擎、卡密核销)有 JUnit 覆盖,含并发安全测试,可作回归基线。
4. **关键设计已做防错加固**:人气值单一入口、流水账只增不改可追溯;金额/积分整数运算无浮点误差;写操作幂等防重复;卡密核销原子抢占+事务保护防并发重复。
5. 每个模块经独立代码审查后合入,审查记录可提供。

## 四、运维需求明细

运维工作分为四类,**分别计价**,便于按实际用量评估:

### A 类|基础技术保障(基础服务费,季度结算)

覆盖系统日常稳定运行的常规工作,**不含全天候值守**:

| 项目 | 要求 |
|---|---|
| 日常巡检 | 服务可用性、数据库备份、阿奇索发货链路的定期检查(非直播时段,工作日巡检即可) |
| 一般 Bug 修复 | 响应 ≤ 1 个工作日,修复 ≤ 3 个工作日 |
| 数据维护支持 | 每轮赛事的轮次配置、选手/团队数据录入支持(有后台界面,操作简单) |
| 环境与备份 | 数据库定期备份、基础运行环境维护 |

> 此项为周期性基础服务,不要求工程师长时间在线待命,以远程响应方式即可满足。

### B 类|投票日关键时段值守(按场次计费)

**仅在投票日(每周日、周一)的两个关键时段需要工程师在线值守**,其余时间无需值守:

| 值守时段 | 说明 |
|---|---|
| 投票开启后的前 30 分钟 | 观众集中涌入,并发高峰,需在线监控并即时处理异常 |
| 投票结束前的 30 分钟 | 最后冲刺,并发再次升高,需在线保障 |

> 投票(真相识破)是节目最重要的观众参与环节之一,这两个时段的稳定性直接影响节目效果。值守按"场次"计费(每个投票日 = 2 个值守时段),节目不运营的周期不产生此项费用。

### C 类|投票日紧急响应(按次计费)

投票日值守时段内若发生紧急情况(高并发导致的服务异常、阻断性 Bug 等),**要求 1 小时内响应并着手处理**。此项作为 B 类的紧急保障补充,按实际发生次数计费。

### D 类|小迭代开发(按人天计费)

预期迭代类型:页面文案/样式调整、后台新增报表或操作项、活动规则参数调整(系统已配置化,多为改配置)、偶发新小功能。预计每周期 2~5 个小迭代,单个多在 1~3 人天。

## 五、一次性需求:企业主体迁移(单独报价,非周期性)

**这是一项独立的一次性工作,与上述周期性运维分开计价。**

**背景**:本项目新企业营业执照刚获批,抖音开放平台要求营业执照满 14 天后才能申请 API 接入。因此 6 月 21 日前,系统使用**老企业主体**进行上线和调试;待新企业的 API 审批通过后,需将系统切换至**新企业主体**。

**迁移内容**(需服务商一次性完成):

| 迁移项 | 说明 |
|---|---|
| 抖音企业号(蓝V)切换 | 从老企业账号切换至新企业账号 |
| 抖店切换 | 订单 API、店铺主体由老企业切换至新企业 |
| 抖音开放平台 API 切换 | 小程序、直播玩法、订单等 API 的主体凭证由老企业切换至新企业 |
| 配置与数据核对 | 切换后核对配置正确性,确保卡密发货、订单查询、直播数据等链路不中断 |

**关键提示(请服务商重点评估)**:
1. 此迁移**预计发生在 2026 年 6 月 21 日之后**,届时**项目经理 John 已不在岗**,迁移需由服务商依据交接文档独立完成,甲方仅能提供有限的远程配合。
2. 切换需尽量保证线上服务不中断或中断时间最短。
3. 请在报价中**单列此项一次性费用**,并说明预计工作量(人天)与可执行的迁移方案。
