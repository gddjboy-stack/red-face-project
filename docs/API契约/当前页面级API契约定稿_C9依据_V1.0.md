# 二、Claude 补充发现(Manus 报告遗漏的问题)

> Manus 看的是墨刀链接的文字与结构,我看的是导出 PDF 的实际视觉,以下问题只有看图才能发现。

## 2.1 🔴 头条问题:数字写真素材的尺度——平台生死级风险

核销成功页与选手详情页使用的写真示例图是**真人性感风格**(吊带、身材凸显构图)。这是整套设计稿最危险的一处,危险程度高于所有文案问题:

1. **抖音对"软色情"素材审核严格**,选秀类小程序用此类图片,大概率审核被拒,或上线后被举报下架;
2. 与项目自己的合规策略**直接冲突**——小程序定位是"才艺展示互动助手",合规包装的核心是去饭圈化、去擦边化;写真走性感路线等于自己把"包装"撕了;
3. 数字写真是**付费权益**(明信片购买核销所得),一旦因素材违规下架,整条卡密变现链路归零。

**整改要求(P0,无讨论空间)**:全部写真素材改为**清新、才艺、舞台风**方向(演出照、才艺展示照、清新生活照)。这同时是给彬少的设计令和给 Vincent 的内容生产标准——后续为每位选手 AI 生成/拍摄写真时,以此为内容红线。

## 2.2 🔴 设计稿标注文字混入了用户界面

两处给开发看的注释被当成界面内容画了进去,直接照稿开发就会出现在用户屏幕上:

- 卡密核销页底部:"卡密核销(手动粘贴·5次锁定)"——这是我草图里的图注
- 选手详情页按钮下:"(跳转能力待确认)"——这是我草图里的开发标注

**整改**:删除。今后设计稿的开发标注一律放画布旁白区,不放页面内。

## 2.3 🟠 真相识破页数据自相矛盾

候选名单是 **1号/5号/8号**,下方"实时识破进度"却是 **3号/5号/8号**——1号在候选里没进度,3号有进度却不在候选里。示例数据错位会误导开发对"候选集合=进度集合"这一逻辑的理解。**整改**:两处数据对齐。

## 2.4 🟠 首页顶部英文"LOVAL LEVEL"疑似拼写错误

"LOVAL"不是英文单词(疑为 LOYAL 之误)。若是有意的品牌造词请确认并统一;若是笔误请修正——这行字在首页顶部,上线后人人可见。

## 2.5 🟡 首页"直播排期"入口(Manus 列了三个,实际是四个)

Manus 建议"联动合作/活动推荐/联系我们"先静态或隐藏,但首页实际有**四个**入口,还有一个"直播排期"。处理同理:P0 一并隐藏或灰置,后端无任何对应能力。

## 2.6 🟡 人气页示例数据笔误

3号写作"陈夏",其余所有页面均为"林夏"。小事,顺手改。

# 三、页面级 API 契约定稿(C9 开发依据,即日生效)

> 以下为正式契约。Manus C9 按此实现 Controller 层;彬少的前端标注、未来第三方维护均以此为准。通用响应包裹:`{ code, message, data }`,code=0 成功。

### API-0 登录(Manus 报告遗漏,所有 me 接口的前提)
```
POST /api/auth/login
请求: { "code": "tt.login返回的code" }
data: { "userId": "脱敏用户标识", "isNewUser": bool }
说明: 后端用 code 调抖音接口换 openid,作为 user_id。
```

### API-1 首页直播状态
```
GET /api/live/home
data: {
  "liveStatus": "live|idle",        // 是否有active轮次
  "roundId": 3, "roundName": "第3轮",
  "currentMode": "player|team|spy|pool|none",
  "targetDisplayName": "3号 林夏 A组",  // 后端聚合好,前端直接渲染
  "targetPopularity": 125800,
  "teamDisplayName": "A组", "teamPopularity": 402500,
  "spyChannelOpen": false,           // 识破入口是否显示
  "updatedAt": 1781234567
}
```

### API-2 人气看板
```
GET /api/popularity/board?tab=player|team|spy&roundId=3
data: {
  "tab": "player", "roundId": 3,
  "spyTabEnabled": false,            // 卧底档是否激活(未激活前端灰置)
  "items": [ { "number": 1, "name": "陈微", "teamName": "A组", "value": 88400 } ]
  // items 按 number 升序,绝不按 value 排序(合规红线)
}
```

### API-3 卡密核销
```
POST /api/tokens/redeem
请求: { "token": "RFZJ-XXXX-XXXX-XXXX" }   // userId 从登录态取,不由前端传
data(成功): {
  "playerNumber": 3, "playerName": "林夏", "teamName": "A组",
  "points": 19900,
  "photoAssetId": "photo_p3_0001", "photoPreviewUrl": "https://...",
  "collected": true
}
失败 code 枚举(前端按码显示固定文案):
  40001 invalid_format / 40002 not_found / 40003 already_used
  40004 locked(data.remainingSeconds) / 40005 round_not_available
```

### API-4 我的写真
```
GET /api/me/photos
data: { "total": 3, "items": [ { "assetId","previewUrl","playerName","createdAt" } ] }
```

### API-5 识破提交(P1,彩排后随 C13)
```
POST /api/suspicion/submit   — 契约随 C13 开卡时定稿,本期不实现
```

**C9 范围裁定**:API-0/1/2/3 必做,API-4 简单列表(一条 SQL),API-5 不做。彩排底线与 Manus 建议一致。
