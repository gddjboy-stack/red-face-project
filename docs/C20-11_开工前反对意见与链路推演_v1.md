## 二、阻塞项 1：折算后分配，裸池该扣多少？——卡片未定义，且无论怎么选都有代价

### 2.1 问题成因

`TeamDistributionService` 的分配是两步走，两步用的是**同一个 `totalValue`**：

```java
long totalValue = valueOrZero(statsMapper.findTeamPopularity(teamId, roundId));   // L70 读
int updatedRows = statsMapper.distributeTeamPopularity(teamId, roundId, totalValue); // L82 扣
```

而 L82 的 SQL 是：

```sql
UPDATE team_round_stats
SET team_popularity = team_popularity - #{totalValue},
    distributed_popularity = distributed_popularity + #{totalValue}
WHERE team_id = #{teamId} AND round_id = #{roundId}
  AND team_popularity >= #{totalValue}
```

**扣减操作的是裸列 `team_popularity`。** 卡片只要求把 L70 改成折算读取，但没说 L82 该扣多少。若照卡片字面执行，结果是：

> 裸池 100 万，系数 80 → L70 读到 80 万 → 分给成员 80 万 → L82 执行 `team_popularity = 100万 - 80万 = 20万`

裸池剩 20 万，团队榜上立刻显示 16 万（20 万 × 0.8）。**运营看到榜上还有 16 万，会再点一次均分**，于是又分出 16 万，池子剩 4 万，榜上显示 3.2 万……可无限点下去。原缺陷是"一次多分 20 万"，改完变成"可反复分配至无穷次"，且每一笔都合规、无告警——**这比原缺陷严重，且同样属于账本错**。

### 2.2 三个方案与各自的代价

我不认为存在无代价的选项，请 Claude 在三者中裁定：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 扣裸池全额** | 读折算值 80 万作分配额，L82 改为按裸池当前值全额清零 | 池子干净，不可重复分配；榜面归零与"已分完"直觉一致 | 扣 100 万只分出 80 万，**差额 20 万无流水解释**。`distributed_popularity` 记 100 万还是 80 万也需定：记 100 万则与成员所得之和不等，记 80 万则与扣减额不等，两者必有一处对不上 |
| **B. 扣折算额** | L82 仍传 80 万 | 扣减与分配额一致，账面自洽 | **可无限重复分配**，最严重，不可接受 |
| **C. 分配后同时把系数归位** | 分配 80 万，扣裸池 100 万，并把 `coefficient` 重置为 100 | 池子干净且不留残值，语义上"系数已在分配时兑现" | 团队系数是**累加域**（`StatsMapper:72` 是 `coefficient = coefficient + delta`），且有独立账本 `team_coefficient_ledger`。归零会让账本与实际系数脱节，后续再加成时基数错乱。且系数还服务于团队榜显示，归零后榜面口径也变 |

**我的倾向是 A，但必须补一条明示的流水**：在分配批次 `team_distribution_batch` 中同时记录裸池扣减额与折算分配额两个字段，让"扣 100 万分出 80 万"这件事在账本里可查，而不是靠事后推算。这样代价从"差额无解释"降为"差额有记录"。但这需要改表结构，属超范围，请 Claude 判定是一并做还是另立卡。

### 2.3 我不建议的做法

有一种看似省事的思路是"把系数折算改到写入端，入池时就乘好"，这样读取端全都不用改。**我反对**：入池时折算会让系数变更无法追溯生效——运营在第 3 笔礼物后才把系数从 100 调到 80，前两笔已按 100 入池，无法回溯。当前"账本存裸值、读取时折算"的范式是正确的，与 C20-10 卧底系数一致，不应打破。

## 三、阻塞项 2：团队系数可以大于 100，卡片示例只覆盖了缩小的情形

卡片的例子是系数 80（×0.8，折算值 < 裸值）。但我核查 `CoefficientService:61 manualAdjustTeam` 发现：

```java
if (Math.abs(delta) > 100) throw new ApiException(400, "单次加成调整不能超过 ±1.0");
```

校验只限制**单次** delta 在 ±100 之内，而该方法**可被反复调用且系数是累加的**。因此：

**系数大于 100 完全可达。** 例如两次 +50，系数变为 200，即 ×2.0。此时裸池 100 万，折算值 200 万。若按方案 A 或 B，L82 的 `WHERE team_popularity >= 200万` 直接不匹配，`updatedRows` 为 0，代码抛出 `IllegalStateException("团队池余额不足或已被并发分配")`。**运营看到的报错是"余额不足"，但榜上明明显示 200 万**——这是最容易引发现场争执的一类错误提示：报错内容与屏幕显示直接矛盾。

**系数还可以为负。** 三次 -100 会让系数变成 -200，折算值为负。此时 `totalValue <= 0` 会走既有的"团队池无可分配人气"分支，行为上不出错，但提示语与实情不符（池子里明明有 100 万裸值）。

因此需要 Claude 裁定：**当折算值超过裸池时，均分该分多少？** 我认为只有两个自洽选项，一是取 `min(折算值, 裸池)` 并明确告知运营"系数放大部分不参与分配"，二是直接拒绝并给出准确提示"团队系数 ×2.0 导致折算值 200 万超过实际池值 100 万，请先核对系数"。我倾向后者，因为前者会让运营以为分完了、实际少分了一半，属于静默错误。

顺带一条建议：`manualAdjustTeam` 应当增加**系数结果值域校验**（例如限定最终系数落在 0 到 300 之间），而不是只校验单次 delta。现状允许把系数累加成任意值，负系数在任何展示路径上都会产生负人气。这属于本卡范围外，是否另立卡请 Claude 判定。

## 五、取整一致性的具体做法

卡片第三节 C 要求分配总额与榜面显示取整后完全相等。我的做法是**新增的 mapper 方法逐字符照抄 `findTeamBoard` 的折算表达式**：

```sql
CAST(COALESCE(team_popularity, 0) * COALESCE(coefficient, 100) / 100 AS SIGNED)
```

不在 Java 里写 `raw * coef / 100`。理由是 H2 与 MySQL 的 `CAST(... AS SIGNED)` 在遇到 `.5` 与负数时的舍入行为与 Java 的整数除法（向零截断）并不保证一致，一旦系数导致出现半数，两处会差 1。让两条路径走完全相同的 SQL 表达式，是唯一能保证"取整路径统一"的做法，也便于日后核对。
