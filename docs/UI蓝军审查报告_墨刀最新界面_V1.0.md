# 《红颜·局中局》墨刀最新界面蓝军审查报告 V1.0

**项目名称：** 红颜·局中局  
**审查对象：** 彬少最新墨刀 UI 原型  
**审查链接：** [墨刀只读原型](https://modao.cc/proto/dg2Fhu1qtgevk1JFgSB75E/sharing?view_mode=read_only&screen=slb3l2lzTtD47KkDzo34IV)  
**审查日期：** 2026-06-12  
**作者：** Manus AI  
**审查定位：** 蓝军审查，优先暴露“设计美观但开发给不了、合规过不了、状态缺失导致上线翻车”的风险。

---

## 1. 总体结论

本次 UI 优化的方向明显比初稿更接近“**直播伴随工具**”定位。首页已经把直播状态、当前环节、当前集赞对象、卡密核销入口和卧底识破入口集中到主路径；人气页也明确写出“按序号排列·不设名次”，说明彬少已经吸收了去排名化要求。核销页和核销成功页已经形成了“复制卡密—粘贴核销—贡献人气—写真入藏”的基本闭环，这是当前版本最值得保留的核心成果。[1]

但从蓝军角度看，当前 UI 仍然存在三个关键风险。第一，**后端业务能力已有，但 API 层尚未形成**；仓库中已实现 `PopularityService`、`CollectStateService`、`TokenService` 等服务层能力，但代码检索未发现 `@RestController`、`@RequestMapping`、`@GetMapping` 或 `@PostMapping` 等面向小程序调用的接口层，因此 UI 不能直接按“接口已可用”理解。[4] [5] [6] 第二，**部分 UI 字段超出当前 `RedeemResult` 和统计查询能力**；例如核销成功页的“会员有效期+7天”、人气页的全量列表、首页的选手姓名与团队名都需要 DTO 聚合或新接口支持。[4] [7] 第三，**合规风险虽然已下降，但仍有敏感词和备用素材误实现风险**；尤其是“集赞”“送礼”“打赏榜单”“看广告”“金币”“积分”“提现”等词必须明确哪些属于正式上线范围，哪些只是墨刀模板残留或备用素材。

| 审查维度 | 当前判断 | 风险级别 | 核心建议 |
| --- | --- | --- | --- |
| 与后端一致性 | 服务层能力较强，但 REST API 与 UI 聚合 DTO 缺失 | 高 | Claude 先补“最小 API 契约”，再让前端接页面。 |
| 合规红线 | 去排名化基本守住，但仍有明星应援、刷量、打赏、虚拟支付语义风险 | 高 | 正式页面禁用“投票/打榜/应援/排名/打赏榜单/提现/金币”等词。 |
| 状态完整性 | 页面主态较完整，但加载、空数据、错误、锁定、提交中状态不足 | 高 | 每个 P0 页面至少补 5 类状态：加载、空、错、无权限、刷新失败。 |
| 核销链路 | 主流程正确，但 placeholder、错误提示和自动收藏字段需对齐后端 | 中高 | 输入格式改为 `RFZJ-XXXX-XXXX-XXXX`，补足错误态和倒计时态。 |
| 开发成本 | 原型中存在大量非 P0 备用页 | 中高 | 严格冻结 P0 范围，备用页不要进入 6/14 彩排开发。 |

## 2. 与已开发后端的一致性审查

目前后端的真实状态可以概括为：“**底层业务规则已开始成型，但尚未提供小程序可直接消费的页面级 API**”。这意味着 UI 不宜再继续大幅扩张页面范围，而应把设计稿切成两层：第一层是 P0 彩排必须实现的页面；第二层是 P1/P2 运营增强页面。否则开发会被迫在没有接口契约的情况下硬拼假数据，导致彩排时 UI 好看但业务不可用。

| UI 页面/模块 | UI 展示内容 | 当前后端支撑情况 | 蓝军判断 | 建议处理 |
| --- | --- | --- | --- | --- |
| 首页直播状态 | “正在直播 · 第3轮”“当前环节”“当前集赞对象” | `CollectStateService` 能维护 `player/team/spy/pool` 当前集赞目标，但只返回原始 mode、targetId、roundId，尚未聚合选手名、团队名和页面文案。[5] | 部分支撑 | 增加 `GET /api/live/state`，返回页面可直接渲染的标题、目标类型、目标名、更新时间。 |
| 首页人气摘要 | “3号 林夏 A组 125,800”“A组团队人气 402,500” | `StatsMapper` 支持单个选手、团队、卧底、总池数值查询，但缺少列表聚合和关联玩家/团队名查询。[7] | 部分支撑 | 首页只显示当前目标和团队摘要，避免扩展复杂看板。 |
| 人气页三档切换 | “个人/团队/卧底” | schema 和 service 支持 player/team/spy/pool 的写入与单值查询；尚缺 UI 列表 API。[6] [7] | 概念支撑，接口不足 | P0 可先实现“个人/团队”，卧底档灰置为“卧底之夜开启后显示”。 |
| 卡密核销页 | 手动粘贴、确认核销、5 次锁定 | `TokenService.redeem` 支持格式校验、防爆破、轮次预检查、原子抢占和错误码返回。[4] | 强支撑 | 可作为 P0 主链路，但 UI 必须补错误态、锁定态、提交中态。 |
| 核销成功页 | 加人气、会员有效期、写真自动收藏 | `RedeemResult` 返回 tokenId、playerId、points、photoAssetId、remainingSeconds；不返回选手名、团队名、会员有效期、写真 URL。[4] | 部分支撑 | “会员有效期+7天”先删除或改成“权益已记录”；写真需由 `photoAssetId` 再查资产 URL。 |
| 我的数字写真 | 收藏数量与收藏列表入口 | `user_photo_collection` 表和插入逻辑存在，但缺少收藏列表读取接口。[8] | 部分支撑 | 增加 `GET /api/me/photos`；没有接口前只显示“核销后自动收藏”。 |
| 真相识破 | 多选怀疑对象、实时识破进度、提交识破 | schema 有 `suspicion_votes` 表，但当前未发现对应 Mapper/Service/Controller；自检清单中 `submit_suspicion` 仍为待核对契约。[9] [10] | 高风险 | 不进 P0，除非 Claude 立刻补最小投票接口与测试。 |
| 订单查询/会员群 | 订单、会员群、用户身份 | 当前仓库未见订单、会员、社群 API | 高风险 | UI 可保留视觉入口，但首期灰置或隐藏。 |

这里最需要提醒 Claude 的不是“后端不会做”，而是“**请先定义页面级接口契约**”。如果继续让前端直接按 UI 图取字段，就会出现每个页面都需要前端拼装数据、后端临时加字段、测试无法稳定复现的问题。建议下一张任务卡不要急于做更多 UI，而是先补四个页面级 API：`live/home`、`popularity/board`、`token/redeem`、`me/photos`。

## 3. 合规红线审查

微信和抖音小程序的运营规范都强调功能、内容、跳转和接口能力必须合法合规，不得诱导分享、刷量、刷票、刷粉、刷单，不得使用接口能力干扰正常流程，也不得让小程序依赖外部 App 才能完成核心功能。[2] [3] 更关键的是，抖音小程序规范中单独列出了“明星应援行为”，明确不得设置明星艺人个人或组合排行榜单，不得设置诱导粉丝打榜的相关功能，不得提供打榜任务、应援集资相关功能或信息。[3]

> 抖音小程序运营规范要求：“小程序内，不得设置各种形式的明星艺人个人或组合的排行榜单，不得设置诱导粉丝打榜的相关功能，不得提供各种打榜任务、应援集资相关功能或信息。”[3]

从这个角度看，彬少这版 UI 已经有两个正确动作。第一，人气页写了“按序号排列·不设名次”，这是明确的去排名化表达。第二，选手页写了“点赞/送礼请在直播间进行”，没有在小程序内部做点赞、送礼按钮，这降低了平台审核风险。[1]

但仍需整改若干文案。首页“当前环节 - 为3号林夏 A组进行集赞”中的“集赞”虽然是内部业务词，但在审核语境里可能被理解为组织刷赞或打榜。建议改成“当前互动归属：3号林夏 A组”或“当前直播互动计入：3号林夏 A组”。“送礼”一词可以保留为直播间事实说明，但不应做成强 CTA；建议改成“直播间互动请回到直播间完成”。“购买选手周边”“打赏榜单”“看广告”“金币”“积分”“提现”等词，如果并非正式上线功能，应从开发交付稿中彻底删除或加醒目的“备用素材，不上线”。

| 当前 UI 词/模块 | 风险原因 | 建议替换或处理 |
| --- | --- | --- |
| 当前环节：进行集赞 | 可能被理解为诱导点赞、刷量或打榜 | 改为“当前直播互动计入：3号林夏 A组”。 |
| 选出你怀疑的人（可多选） | “投票”语义虽未出现，但实质为投票，需要接口和规则披露 | 改为“提交剧情判断”，并补“仅用于节目互动，不产生名次”。 |
| 实时识破进度 65% | 百分比容易形成即时竞争刺激 | 保留可以，但不展示排名，只展示“剧情热度分布”。 |
| 打赏榜单 | 明确高风险，可能触碰榜单/打赏/应援 | 正式交付稿删除，不进入代码。 |
| 金币、积分、提现、看广告 | 容易触发网赚、虚拟支付、广告变现和提现审查 | 正式交付稿删除；如未来需要，另做合规方案。 |
| 会员有效期+7天 | 涉及付费权益与虚拟服务交付 | 若未有订单和会员系统，先删除或改为“权益已记录”。 |

## 4. 状态完整性审查

这版 UI 的主态已经可看，但状态完整性仍是短板。状态设计不是“美术补几张空页面”，而是前后端契约的一部分。比如卡密核销页如果没有 `invalid_format`、`not_found`、`already_used`、`locked`、`round_not_available` 的对应展示，就会导致后端明明返回了正确错误码，用户却只看到模糊失败提示。[4]

| 页面 | 必补状态 | 触发条件 | 后端/前端处理建议 |
| --- | --- | --- | --- |
| 首页 | 直播未开始、直播已结束、场控未设置、数据刷新失败 | 无 active/upcoming round、collect_state 为空、网络失败 | 使用统一状态卡，不要把空白页当正常状态。 |
| 人气页 | 加载中、空列表、刷新失败、卧底档未开启、数据延迟提示 | stats 查询为空、接口错误、卧底夜未激活 | 增加“数据可能延迟 1-2 秒”的弱提示。 |
| 卡密核销 | 输入为空、格式错误、卡密不存在、已核销、锁定倒计时、提交中 | 后端错误码：`invalid_format`、`not_found`、`already_used`、`locked` | 每个错误码对应固定文案；提交中按钮置灰防重复点击。 |
| 核销成功 | 写真加载失败、写真已收藏但预览失败、权益记录成功但网络断开 | photoAssetId 有值但图片 URL 获取失败 | 允许用户返回“我的数字写真”稍后查看。 |
| 我的 | 未登录、无写真、写真加载失败、订单功能未开放 | 用户身份缺失、收藏为空、接口未开放 | 首期不要展示无法点击的订单/会员群强入口。 |
| 真相识破 | 未开启、已提交、重复提交、提交失败、结果冻结 | 卧底轮次未激活、用户已投、接口失败 | 如未实现接口，P0 隐藏或只显示“直播间开启后开放”。 |

需要特别指出的是，微信小程序规范明确提到不得滥用剪切板接口，尤其是用户未操作时默认读取剪切板信息属于风险行为。[2] 抖音小程序规范也要求不得在用户未进行任何操作的情况下默认读取用户剪贴板信息。[3] 因此，“自动检测剪贴板”如果进入实现，必须变成“用户点击粘贴后读取”，不能页面一打开就自动读。

## 5. 核销流程专项审查

核销流程是当前最成熟、也最值得优先打磨的闭环。UI 的“手动粘贴·5次锁定”方向与后端实现基本一致；后端 `TokenService` 已经采用规范化输入、格式校验、防爆破、轮次预检查、条件更新抢占、人气入账、写真收藏的固定流程，并通过 `RedeemResult` 返回成功或错误状态。[4]

当前需要修正的第一处细节是输入占位符。UI 里显示 `XXXX-XXXX-XXXX-XXXX`，但后端正则要求格式是 `RFZJ-XXXX-XXXX-XXXX`，字符集排除了 `0/1/I/L/O` 等易混字符。[4] [11] 因此输入框 placeholder 应直接写 `RFZJ-2345-6789-ABCD` 或 `RFZJ-XXXX-XXXX-XXXX`，不要写四段随机字符，避免用户误以为没有固定前缀。

第二处细节是核销成功页字段。当前 UI 文案“已为3号林夏 A组 +19,900人气值”需要后端返回选手名和团队名，`RedeemResult` 当前只返回 `playerId`，并不返回 `playerName` 或 `teamName`。[4] 如果前端不能稳定查到选手详情，就会出现成功页只能展示“已为3号选手 +19,900人气值”。建议 Claude 在 `redeem` 接口上补一个页面级响应 DTO，至少包含 `playerNumber`、`playerName`、`teamName`、`points`、`photoAssetId`、`photoPreviewUrl`、`message`。

第三处细节是“会员有效期+7天”。当前 tokens 表中有 `product_sku`、`order_id`，但没有会员有效期字段；`RedeemResult` 也不返回会员有效期。[4] [9] 如果这不是已确认的阿奇索权益，建议暂时删除。更稳妥的表达是“数字写真已自动存入我的收藏”，不要额外承诺会员天数。

## 7. 给彬少的设计修改建议

彬少这版视觉气质已经可用，问题不在“好不好看”，而在“哪些元素会误导开发和审核”。我建议他下一版不要继续扩展新页面，而是把现有页面做成“可开发标注版”。每个页面右侧或旁边标出三类信息：第一，哪些元素是 P0 必做；第二，哪些元素是静态展示；第三，哪些元素是 P1/P2 备用素材。这样 Claude 和小程序开发不会把墨刀里的“进入直播间（打赏榜单）”“金币”“积分”“提现”等模板页误当成需求。

在视觉层面，建议统一把“橙色按钮”定义为“业务提交或主路径”，把“白底描边按钮”定义为“跳转或查看”，把灰色区域定义为“暂未开放/不可用”。当前页面里按钮层级基本清晰，但“联动合作、活动推荐、联系我们、加入会员群、订单查询”这些入口混在主路径里，会稀释卡密核销和直播伴随主链路。

## 8. 给 Claude/开发的接口建议

在进入更多前端开发前，建议先补最小页面级 API。否则 UI 对接会陷入“页面字段临时拼、错误码各自解释、状态无法复用”的问题。

| API 建议 | 用途 | 最小返回字段 |
| --- | --- | --- |
| `GET /api/live/home` | 首页直播状态与当前互动归属 | `liveStatus`、`roundId`、`roundName`、`currentMode`、`targetId`、`targetDisplayName`、`targetPopularity`、`teamPopularity`、`updatedAt` |
| `GET /api/popularity/board?tab=player/team/spy` | 人气页三档切换 | `tab`、`roundId`、`items[]`，其中 item 包含 `number`、`name`、`teamName`、`value`，并按 number 排序 |
| `POST /api/tokens/redeem` | 卡密核销 | `success`、`code`、`message`、`tokenId`、`playerNumber`、`playerName`、`teamName`、`points`、`photoAssetId`、`photoPreviewUrl`、`remainingSeconds` |
| `GET /api/me/photos` | 我的数字写真 | `total`、`items[]`，其中 item 包含 `assetId`、`previewUrl`、`playerName`、`createdAt` |
| `POST /api/suspicion/submit` | 真相识破，P1 | `success`、`code`、`message`，并必须有防重复提交和活动状态校验 |

如果时间紧，P0 只建议做前三个接口：`live/home`、`popularity/board`、`tokens/redeem`。`me/photos` 可以只做简单列表，`suspicion/submit` 延后。

## 9. 6/14 彩排优先级建议

我建议 John 在项目管理上明确“**彩排不是完整上线，彩排只验证主链路**”。本次 UI 的 P0 应只包含：首页、选手详情的基础展示、人气页个人/团队看板、卡密核销、核销成功、我的写真入口。P1 包含真相识破、卧底进度、会员群、订单查询、相关视频。P2 才考虑会员、周边、小黄车、广告、金币、积分、提现等商业化和平台能力强相关模块。

| 优先级 | 模块 | 理由 |
| --- | --- | --- |
| P0 | 首页直播伴随、卡密核销、核销成功、人气页个人/团队、我的数字写真入口 | 对直播彩排和阿奇索卡密链路最关键，且已有后端基础。 |
| P1 | 真相识破、卧底进度、选手详情扩展、写真列表 | 有娱乐价值，但接口和状态需补齐。 |
| P2 | 会员群、订单查询、购买周边、直播间跳转增强、广告、金币、积分、提现 | 涉及平台能力、合规审核、商业闭环和额外系统。 |

## 10. 结论与下一步

我的蓝军结论是：**彬少这版 UI 可以作为视觉方向定稿，但不能作为开发范围定稿**。它已经具备直播伴随工具的气质和主链路，但需要在进入开发前完成一次“接口契约瘦身”和“合规词清洗”。如果不做这一步，最大的风险不是页面做不出来，而是开发把备用素材也做了、接口临时拼了、审核词踩线了，最终拖慢 6/14 彩排。

建议下一步由 John 确认 P0 范围，彬少按本报告修改正式开发交付稿，Claude 则优先补页面级 API 契约。Manus 可以继续承担蓝军复审角色，在 Claude 回应接口方案后，再做第二轮“UI—API—测试用例”三方对齐审查。
