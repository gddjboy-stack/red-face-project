## 〇、总评:方案成熟,批准编码

这份方案在三个最敏感的地方都判断对了,值得肯定:
1. **合规包装**:全程"识破/判断/线索/真相"措辞,按序号排列、不做排行榜,候选与进度集合一致——守住了"卧底投票伪装成真相识破进度"这条平台合规生命线。
2. **防剧透**:用户侧 API 坚决不返回 isSpy/真实卧底身份——这是节目悬念的命门,泄露了卧底是谁,整个玩法就废了。它主动识别出这一点,很专业。
3. **最小闭环**:不做自动揭晓/奖励/淘汰/回滚,只做"能参与、能讲清、能审计"的最小版——适合今晚内测,不贪大。

## 六个问题裁定

### C13-Q1:spyChannelOpen 由 active 轮次 + collect_state.mode='spy' 决定 → ✅ 批准
复用 C10 场控的"集赞目标切换"来开关识破入口,不新增活动开关表,是最聪明的最小方案。**批准修改 LiveHomeService**(把当前写死的 false 改为按规则判断)。**边界**:只改 spyChannelOpen 这一个字段的计算逻辑,LiveHomeService 其余不动。

### C13-Q2:每用户每轮只能提交一次 → ✅ 批准,且这是必须修的正确发现
Manus 准确指出:现有唯一键 `uq_user_round_suspect` 只能防"同一用户对同一候选重复投",防不住"同一用户对多个候选分别投"。所以 Service 层必须先查 `userId + roundId` 是否已有任意记录,命中就返回 already_submitted。**批准,且这是关键正确性点,务必落实并写测试验证。**

### C13-Q3:候选来自当前轮次 player_round,排除 eliminated → ✅ 批准
候选 = 当前轮 player_round 中 status 为 normal/free 的选手,排除已淘汰。按 number ASC 排序,严禁按提交数/比例/人气排序。采纳。

### C13-Q4:用户侧 API 禁止返回 isSpy/真实卧底身份 → ✅ 批准(防剧透红线)
这是硬红线。status API 的 candidates 里**绝不能含 isSpy 字段或任何能推断卧底的信息**;`actualSpyPlayerId` 默认不返回。审查时我会专门核验返回 JSON 里没有泄露字段。采纳。

### C13-Q5:暂不做自动揭晓/奖励/回滚/复杂配置 → ✅ 批准
采纳。揭晓由直播间主持人口播("以直播间揭晓为准"),C13 不自动改 player_status、不发奖励。这些复杂逻辑(尤其涉及奖励发放)留到彩排后慎做。最小闭环优先。

### C13-Q6:后台监控卡片可选,不阻塞用户侧 → ✅ 批准
采纳。优先做用户侧闭环(status + submit + 页面),后台识破分布监控卡片时间够就做、不够就先跳过。但建议:**如果今晚内测想演示"实时看大家怎么投",这个监控卡片很出彩,有余力尽量做。**

## 一、补充强调(编码须遵守)

1. **防剧透是 C13 第一红线**:再强调一次,用户侧任何接口、任何字段都不能泄露谁是卧底。审查会专门查这一点。
2. **一次提交限制要有事务保护**:校验开启→校验候选→查重(userId+roundId)→插入,全程 @Transactional,防并发下绕过"一次"限制。
3. **合规文案按方案第三部分**:无"第几名/领先/冲榜",进度条按序号排,候选与进度集合一致(解决早期 UI 审查发现的"候选1号、进度3号"错位问题)。
4. **不碰 C1~C12 主链路**:只新增 Suspicion 相关类 + 改 LiveHomeService 的一个字段 + 小程序加一页,不动其他。
