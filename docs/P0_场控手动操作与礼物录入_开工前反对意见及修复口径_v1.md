# P0 场控手动操作与礼物录入：开工前反对意见及修复口径 v1

**文档状态**：待 Claude 裁定；本文不包含业务代码改动。  
**发起人**：Manus AI（蓝军核查）  
**日期**：2026-08-14  
**关联问题**：

1. 场控后台「手动调分」确认后出现“服务器内部错误”。
2. 场控后台「手动加成」确认后，运营观察到分数没有变化。
3. 集赞目标为团队（`team`）或总池（`pool`）时，「直播数据录入」禁用“音浪（礼物）”一栏；发起人确认这是此前对业务要求的错误理解。

## 一、已确认事实

| 编号 | 核查结论 | 代码证据 | 影响 |
| --- | --- | --- | --- |
| F-01 | 手动调分的前端本应在提交前校验：非总池模式必须选择目标。现场截图中“目标”为“请选择目标”，若当时确实未选择，正确体验应是前端提示“请选择目标”，而不是请求后 500。 | `App.vue`：`submitManualAdjust` 的 `targetId` 非空判断；`AdminControlService.manualAdjust` 仍未独立校验 `targetId`。 | 前端与服务层没有形成双侧防线；无效请求可因其他调用路径或前后端版本不一致演变成不透明的 500。 |
| F-02 | 本地现有有效参数的手动调分接口测试通过：`player=101, round=1, rawValue=88` 会写人气流水和审计日志。 | `AdminControlControllerC10Test.manualAdjustShouldUsePopularityServiceAndWriteAuditLog`。 | 当前代码不能复现“有效已选目标仍 500”；生产站点可能存在已部署版本落后于仓库、请求参数不同或运行时数据不完整，必须加可诊断测试和错误信息后再下结论。 |
| F-03 | 手动加成确实只修改系数，不直接修改人气裸值。`delta=10` 表示系数从 `100`（×1.00）变为 `110`（×1.10）。 | `CoefficientService.manualAdjustPlayer/manualAdjustTeam` 与 `AppConstants.COEFFICIENT_BASE=100`。 | 若场控人员观察的是原始人气值，操作成功后显示不会改变。 |
| F-04 | **选手手动加成目前没有任何已投入使用的可见消费点**：个人榜读取 `individual_popularity` 裸值；场控首页个人目标也读取裸值；最终积分的 `PopularityService.computeScore` 虽会乘选手系数，但全仓没有调用方。 | `C9QueryMapper.findPlayerBoard`、`LiveHomeService.fillPlayerTarget`、全库 `grep computeScore`。 | 对“选手 player”执行手动加成后，即使账本、系数值均成功更新，也没有可见的分数或现行流程会使用该系数。此问题不是提示文案问题，而是业务结果未接入。 |
| F-05 | 团队榜与卧底榜已在查询时乘相应系数；但场控首页团队目标仍读裸值。团队手动加成在不同界面可能出现“榜单变化、顶部监控不变”。 | `C9QueryMapper.findTeamBoard/findSpyBoard`；`LiveHomeService.fillTeamTarget`。 | 与已挂起的 C20-11（团队人气折算读取不一致）存在重叠，不能静默在本修复中改变团队折算的账本语义。 |
| F-06 | 礼物录入被前端及后端同时明确限制为 `player/spy`：前端禁用输入框，后端 `requireGiftAttributableCollect()` 也拒绝 `team/pool`。 | `App.vue` 的 `giftAttributable` / `submitMetricRows`；`LiveMetricEntryService.requireGiftAttributableCollect()`。 | 当前在团队、总池直播环节无法录入全场音浪累计数，水位线也不能推进。 |
| F-07 | 人气引擎本身已完整支持将礼物记入团队或总池：`targetType=team` 会累计团队池，`targetType=pool,targetId=null` 会累计总池。 | `PopularityService.resolveTarget/updateStats`。 | 礼物禁用不是数据模型限制，而是错误的场控资格判断；可在不新增表结构的情况下修正。 |
| F-08 | 现场所需口径已由发起人明确：**礼物是全局直播数据来源。集赞目标切换为选手、团队、卧底或总池时都必须允许录入；模式决定归属，不能决定能否录入。** | 发起人 2026-08-14 反馈及截图。 | 此口径将作为礼物修复的基准。 |

## 二、反对意见：不能只做“去掉禁用”和“补一个 try/catch”

### 2.1 反对只删除礼物禁用条件

若只删除前端 `disabled`，后端仍会拒绝团队与总池模式；若只改后端，前端仍不允许输入。两端必须同改，并要用测试覆盖四种模式。

此外，礼物是全场累计数。切换目标前若未先录入，切换前累积的整段音浪会归给新目标。既有的切换前水位线预警仍必须保留，不能因为允许 `team/pool` 而被删掉。

### 2.2 反对将手动加成伪装成“已经影响分数”

现有选手加成写的是系数账本而不是人气账本，更新后裸人气不会变化。这本身可以是正确的设计；但当前没有任何现行榜单、场控首页或结算调用消费该选手系数。因此，系统实际状态是：

> 操作可成功，审计可留痕，但对选手没有可见或已接入的业务效果。

仅补一个“加成成功”吐司或刷新页面，会继续误导场控人员。必须明确其**生效展示与结算消费点**，否则应暂时隐藏选手手动加成入口而非允许现场使用。

### 2.3 反对把生产 500 直接归咎于截图中的“未选目标”

截图呈现的是“目标未选”。当前前端本应在这一状态下阻止提交；仓库内的有效参数测试也通过。因此，不能在没有生产请求体、部署版本号和服务端堆栈的情况下，武断宣称根因已确认。

但修复方向无争议：服务层也必须校验目标 ID、目标存在性和轮次归属；前端应在确认前把“目标/轮次/变动/原因”完整回显。这样即使生产数据错误，也得到可操作的 400 业务提示，而非“服务器内部错误”。

## 三、建议的修复范围（待裁定后实施）

| 模块 | 建议改动 | 预期结果 |
| --- | --- | --- |
| 手动调分 | 前端增加目标、轮次、非零变动、原因的显式校验；服务层补齐 `targetId`、允许类型、目标存在性与目标本轮归属校验；将数据冲突映射为明确 400/409。 | 任何无效输入不再出现 500；正确输入写入人气流水与审计日志。 |
| 手动加成 | 使用与手动调分同样的下拉目标/轮次选择控件，去掉裸 `ID` 输入；补齐非空原因、目标/轮次存在性校验；接口返回“调整前系数、delta、调整后系数、折算后的可见值”。 | 场控可确认对象正确，且点击后能看到“是否真正生效”。 |
| 选手加成消费点 | 按 Claude 对 Q1 的裁定，接入个人榜/结算读模型，或临时下线选手加成。 | 选手加成不再是“写入后无任何业务效果”的死操作。 |

| 取证与回归 | 新增 MockMvc/服务层测试：手动调分的四类目标及非法输入、手动加成可见结果、四种模式礼物录入、切换前水位线预警未回归；浏览器实测截图。 | 防止本次缺陷因“只测选手模式”再次复发。 |

## 四、请 Claude 裁定的事项

### Q1：选手“手动加成”究竟应影响哪一个对外结果？

当前实现名为“加成系数”，`delta=10` 为 +10%，但个人榜和场控首页均不折算，最终积分计算也没有调用方。必须三选一：

| 选项 | 含义 | 我的意见 |
| --- | --- | --- |
| A | 个人榜及现场场控目标值按 `individual_popularity × coefficient / 100` 展示；保留裸值供审计。 | **推荐。** 与团队、卧底折算范式一致，且场控点击后可验证效果。需同时把“裸值/折算值”在管理端明确区分。 |
| B | 只在尚未接入的结算环节使用系数；在该结算落地前隐藏选手手动加成。 | 次选。语义严格，但会失去直播现场调控能力。 |
| C | 将手动加成改为直接人气变动。 | 不推荐。会混淆“调分”和“系数加成”，破坏既有账本语义。 |

### Q2：团队手动加成是否与 C20-11 合并处理？

团队榜已折算、场控首页未折算，正是 C20-11 已登记的不一致。建议本次只补交互、校验与可见回执，**不在本卡顺手改团队人气均分/扣减账本逻辑**；关于首页折算是否同步，纳入 C20-11 裁定后的实现。

> 我的意见：接受该拆分，防止一个 P0 修复悄然改写团队账本规则。

### Q3：礼物的轮次以哪个来源为准？

当前集赞目标保存了 `roundId`，而现有礼物入账代码另行使用“当前可入账轮次”。正常直播两者相同，但一旦后台选择了非当前轮次，可能出现“目标显示在 A 轮、礼物记到 B 轮”。

| 选项 | 规则 | 我的意见 |
| --- | --- | --- |
| A | 礼物一律使用当前可入账轮次；切换目标时要求其轮次必须等于当前可入账轮次。 | **推荐。** 规则单一、避免跨轮礼物污染。 |
| B | 礼物使用集赞目标所保存的轮次。 | 不推荐，容易把当前直播数据写到历史/未来轮次。 |

## 五、当前测试盲区

现有回归测试显示：有效的选手手动调分、选手模式礼物水位线录入均通过；但以下路径没有测试覆盖：

1. 手动调分的 `team`、`spy`、`pool` 以及空目标/错轮次/不存在目标。
2. `/api/admin/adjust-coefficient` 的选手与团队手动加成，以及成功后回显的系数和可见结果。
3. `team` 与 `pool` 模式的礼物水位线预览、入账、归属和切换前预警。
4. 选手系数在任何实际场控读模型或结算读模型中的消费。

**结论**：本问题暴露的是“后端单点 happy-path 测试通过，但场控端到端操作失败/无可见效果”的测试策略缺口。后续验收必须以四种目标模式的端到端链路为单位，而不是只验证单个 Service 写库成功。
