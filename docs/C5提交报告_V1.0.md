## 二、关键流程说明

C5 的 `TokenService.redeem()` 严格遵守 Claude 裁定后的流程顺序：输入规范化、防爆破检查、轮次预检查、原子抢占卡密、人气入账、写真收藏。特别是轮次检查被放在原子抢占之前，因此当系统没有 active 或 upcoming 轮次时，`redeem()` 会直接返回 `round_not_available`，此时不会执行 `UPDATE tokens`，卡密仍保持 `unused`。

| 步骤 | 实现要点 | 风险控制 |
|---|---|---|
| 输入规范化 | `trim → 全角转半角 → 大写 → RFZJ-XXXX-XXXX-XXXX 格式校验` | 拒绝非法格式，防止脏数据进入核销流程 |
| 防爆破检查 | `FailureCounter` 使用内存 Map 记录连续失败次数 | 连续失败 5 次后第 6 次返回 `locked` |
| 轮次预检查 | `RoundService.getCurrentAccrualRoundId()` | 无可用轮次时卡密不被消耗 |
| 原子抢占 | `UPDATE tokens SET status='used' ... WHERE token_id=? AND status='unused'` | 并发下只有一个线程能成功 |
| 人气入账 | `PopularityService.applyChange(source="token", idempotencyKey="token_" + token)` | 继续遵守全系统唯一人气入口 |
| 写真收藏 | 插入 `user_photo_collection`，唯一键冲突捕获忽略 | 重复收藏不影响核销主流程 |

## 五、蓝军说明与待审查点

第一，`TokenService` 中为了区分 already_used 与 not_found，在原子抢占失败后才调用 `tokenMapper.findById(token)`。这不是“先 SELECT 再 UPDATE”，而是失败后的状态区分，符合手册 5.2 中“此时可 SELECT 区分 not_found 和 already_used”的说明。

第二，轮次不可用检查位于原子抢占之前，严格落实 Claude 方案 E 的“防止把卡密烧掉”要求。对应 JUnit 明确断言了 `round_not_available` 时 `tokens.status` 仍为 `unused`，且 `popularity_ledger` 中没有 `token_卡密` 流水。

第三，防爆破计数器在实现过程中发现一个边界问题：未锁定状态的 `lockedUntil=0` 不应被 `isLocked()` 当作过期状态删除，否则失败次数无法累计。该问题已修复，并由“连续失败 5 次后第 6 次 locked”的测试覆盖。

第四，本次并发核销测试使用 `CountDownLatch` 使两个线程同时发车，并断言成功数为 1、ledger 幂等流水为 1、统计表仅增加一次。该测试验证了 `UPDATE ... WHERE status='unused'` 原子抢占的核心并发约束。
