## 〇、总评:方案专业,批准编码

这份方案最有价值的是一个**真实的平台技术发现**:抖音外部 H5 唤起小程序,不像微信那样可以手写 URL Scheme,必须用平台接口生成的跳转链接。Manus 没有臆造一个假的 `snssdk1128://` 协议硬编码进去(那样会在真实测试时死链),而是查了抖音官方文档后做了"配置化链接 + 复制降级"的稳妥设计。这种"不确定平台能力就不硬编码、留降级路径"的判断,正是这张集成卡最需要的工程审慎。批准。

## 六个问题裁定

### C12-Q1:允许改小程序核销页加 query token 预填 → ✅ 批准
这是 H5 带 token 落地的最小必要改动,且不破坏 C11 合规红线(仍不自动读剪贴板、不自动核销、用户必须点"确认核销")。采纳。**边界**:只在 onLoad 读 options.token 预填输入框,其余一行不动。

### C12-Q2:H5 跳小程序用"配置化链接 + 复制降级",不硬编码未验证 scheme → ✅ 批准(关键正确)
这是本卡最重要的裁定。**采纳,且强调:绝不允许硬编码臆想的跳转协议。** 三层策略(A 配置化链接 / B 复制降级 / C 后端生成链接)设计合理。彩排阶段:
- 如果到时拿到了抖音官方跳转链接 → 填进 `miniProgramLinkBase`,走自动跳转
- 如果没拿到 → `miniProgramLinkBase` 留空,只显示"复制卡密 + 手动打开小程序核销页"的降级路径,**不显示"自动打开"的承诺,不制造死链**

这个降级设计保证了:即使跳转能力没就绪,彩排/测试也能用"复制卡密→手动进小程序核销"跑通,不会卡死。非常对。

### C12-Q3:暂不新增后端生成跳转链接接口 → ✅ 批准
采纳。生成抖音跳转链接需要 AppID/Secret/client_token,而这些现在还没配(依赖企业主体和 API 权限)。**现在做这个接口会被平台接入拖死,且纯 H5 里放密钥不安全。** 暂不做,留到 6/22 真实环境测试时,若官方能力就绪再补。这与项目整体节奏一致。

### C12-Q4:oid 仅展示不上报后端 → ✅ 批准
采纳。核销凭证是 token,oid(订单号)在彩排阶段仅展示/调试用。订单追踪是退款(C14)和后续的事,C12 不碰。保持核销链路简单。

### C12-Q5:真机/开发者工具截图纳入 6/22 测试,本卡交代码+联调清单 → ✅ 批准
采纳,且这与我们的整体安排完全吻合:C12 在**开发环境**用模拟器跑通全链路(出代码+联调清单+截图),**真机和真实云环境验证留到 6/22**(那时运维方已部署到云、可接入真实抖音环境)。分两步是对的。

### C12-Q6:本地启动三端补截图 → 裁定:做,但按"尽力而为",不阻塞
采纳 Manus 建议,略作明确:**C12 的核心交付是"H5代码 + 核销页预填 + 可执行的全链路联调清单"**;本地三端联调截图**尽量做**(能做出来对 6/22 测试是很好的预演和信心),但如果本地三端同时跑起来有环境困难,**以"详细到可照做的联调清单"为准**,截图不作为唯一阻塞标准。理由:三端(后端+Vue后台+小程序)本地同时跑起来对环境有要求,不必为截图卡住编码;真正的端到端真机验证反正在 6/22 云环境做。
