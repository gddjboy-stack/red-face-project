## 三、Bug 1：新增选手/新增队伍时报 JSON 解析错误

### 3.1 现象

用户在管理后台“基础数据”页点击“新增选手”或“新增队伍”时，页面顶部出现红色错误提示：`Unexpected token '<', '<!doctype ... is not valid JSON`。该错误从用户视角看起来像“新增失败”，但后台表格有时会实际新增成功，导致操作者不确定数据是否已经写入。

### 3.2 排查结论

排查时我分别用本地后端地址和临时公网管理后台代理地址调用新增接口，`POST /api/admin/players` 与 `POST /api/admin/teams` 都能正常返回 JSON，并且数据可以写入演示库。因此，这不是后端新增接口不可用，也不是数据库写入失败。问题更接近前端表单默认提交或浏览器默认行为引发的非 API 请求：后端日志中出现大量 `POST path=/ status=500`，而用户看到的 `<!doctype ...` 说明前端收到的是 HTML 页面，却被当作 JSON 解析。[5]

| 排查项 | 结果 | 含义 |
|---|---|---|
| 本地 `POST /api/admin/players` | 成功返回 `application/json` | 后端新增选手接口可用 |
| 公网代理 `POST /api/admin/players` | 成功返回 `application/json` | Vite 代理可转发 API 写请求 |
| 本地/公网 `POST /api/admin/teams` | 成功返回 `application/json` | 后端新增队伍接口可用 |
| 后端日志 `POST path=/ status=500` | 出现多次 | 前端有额外根路径 POST 请求 |
| 用户错误 `Unexpected token '<'` | 返回内容以 HTML doctype 开头 | 前端把 HTML 当 JSON 解析 |

### 3.3 临时处理方案

在隔离演示工作区中，我已做两项演示环境级修复。第一，为 Vite 开发服务器增加 `allowedHosts: true`，解决临时公网域名访问管理后台时的 Host 校验问题。第二，在管理后台主容器上增加 `@submit.prevent`，阻止页面内表单误提交，从而避免输入框回车或默认提交行为触发根路径 POST。[5]

```diff
diff --git a/frontend/control-admin/src/App.vue b/frontend/control-admin/src/App.vue
@@
-  <main class="admin-shell">
+  <main class="admin-shell" @submit.prevent>
```

```diff
diff --git a/frontend/control-admin/vite.config.ts b/frontend/control-admin/vite.config.ts
@@
   server: {
     port: 5173,
+    allowedHosts: true,
     proxy: {
```

临时修复后，我用浏览器实际点击“新增选手”和“新增队伍”进行验证，页面能够出现“选手已新增”“队伍已新增”，表格也同步显示新增行，且不再出现 `Unexpected token '<'` 错误。随后我通过重启演示环境将测试数据复位，确保今晚环境回到初始 DEMO 数据。

### 3.4 建议 Claude 进入正式代码的处理

建议 Claude 不要简单照抄演示环境的 `allowedHosts: true` 进入生产配置。`@submit.prevent` 或等价的“禁用默认表单提交”应进入正式后台代码；而 `allowedHosts` 应拆分为开发/演示 profile 或环境变量配置，避免生产环境误放开 Host 限制。

| 修复项 | 是否建议进正式代码 | Claude 处理建议 |
|---|---|---|
| 禁止后台页面默认表单提交 | 是 | 在 `App.vue` 或表单组件级加 `@submit.prevent`，并检查所有按钮是否显式 `type="button"` |
| API 错误处理 | 是 | 当前遇到 HTML 响应时直接抛 JSON parse，建议先检查 `content-type`，给出“接口返回非 JSON，请检查代理/服务状态”的中文提示 |
| Vite `allowedHosts: true` | 不建议直接进生产 | 仅用于演示/开发域名，正式环境应使用明确 allowlist 或部署层配置 |
| 新增后表单清空与序号递增 | 建议 | 新增成功后清空姓名/队名，并将选手序号自动设为当前最大序号 + 1 |

## 四、Bug/体验问题 2：分队与卧底设置依赖 ID，非技术人员难操作

### 4.1 现象

用户在“分队与卧底设置”区域看到的是“轮次 ID、选手 ID、队伍 ID、是否卧底、状态”这些字段。虽然从技术上这套表单可以工作，但 John/Vincent 需要手动查表记 ID，并理解 `normal/free/eliminated` 的英文含义。这种设计更像开发调试界面，而不是运营后台。

### 4.2 蓝军判断

该问题不一定是后端 bug，但属于正式内测前必须优化的**高风险运营体验问题**。直播现场或内测会中，一旦操作人员把选手 ID 与队伍 ID 填错，就可能造成错误分队、错误卧底、错误状态。更严重的是，卧底身份属于玩法核心信息，误设或误展示会直接影响直播悬念。

| 当前字段 | 当前风险 | 正式版建议 |
|---|---|---|
| 轮次 ID | 操作员不知道当前轮次 ID，容易填错 | 改为“轮次名称下拉”，展示 `1 · DEMO_第1轮_缘分初见 · active` |
| 选手 ID | 需要记住选手编号与数据库 ID 的差异 | 改为“选手下拉”，展示 `2号 DEMO_小蓝` |
| 队伍 ID | 需要查队伍 ID | 改为“队伍下拉”，展示 `DEMO_A组` |
| 是否卧底 | 当前开关语义不够明确 | 保留开关，但旁边文案改为“设为本轮卧底” |
| 状态 | 英文枚举对运营不友好 | 中文展示：正常 / 自由人 / 已淘汰；提交时映射为 `normal/free/eliminated` |
| 保存反馈 | 当前不够具象 | 保存后提示“已将 2号 DEMO_小蓝 设置为 DEMO_A组卧底” |

### 4.3 建议 Claude 的实现方式

建议正式优化不要改后端数据模型，只在管理后台前端做组合数据展示和提交前映射。前端可读取已有 `players`、`teams`、`rounds` 和 `player-round` 数据，形成下拉选择项。提交时仍调用现有 upsert 接口，保持后端契约稳定。[7]

> 建议 Claude 把该项定义为 **C19/C13 后台分队与卧底设置 UI 优化**。这不是今晚演示必须补丁，但应进入下一轮正式开发，否则运营人员仍需依赖技术人员在场。

## 五、问题 3：演示环境与正式环境边界需要更清晰

今晚采用方案B后，团队可以打开临时公网链接看到真实运行页面，这对内测很有价值。但从项目经理视角看，演示环境越像真实系统，越容易让非技术成员误以为“已经可以上线”。因此后续文档和 UI 上都应强化环境标识。

| 风险点 | 今晚处理 | 后续建议 |
|---|---|---|
| 演示库与生产库混淆 | 数据均带 `DEMO_` 前缀 | 后台顶部增加醒目的“DEMO 环境 / 数据会重置”标识 |
| 临时公网链接被误当线上地址 | 口头说明临时有效 | 页面 footer 显示“临时演示链接，不可用于正式直播” |
| H2 内存库重启即清空 | 通过脚本可复位 | 演示脚本中明确“重启会丢失现场新增数据” |
| Vite 开发服务用于演示 | 已可访问 | 正式演示应考虑构建静态包或部署到稳定预发环境 |

## 六、问题 4：H5 Bridge 当前仍是复制降级，不是自动跳小程序

H5 Bridge 今晚可正确展示核销凭证、订单号与手动核销路径，并明确提示“当前未配置平台跳转链接”。这符合当前边界，也避免了伪造尚未验证的平台跳转能力。[3]

但对真实用户而言，复制卡密再打开小程序仍是阻力。正式链路应继续推进抖音平台能力、真实小程序 appid、体验版/线上版路径与 H5 跳转参数验证。若 6/22 前无法完成自动跳转，则需要在 UI 上把复制降级做得更顺滑，例如一键复制后展示“去抖音搜索小程序”的图文步骤。

| 项目 | 当前状态 | 后续建议 |
|---|---|---|
| H5 参数展示 | 已可用 | 保留 |
| 自动跳小程序 | 未验证 | 6/22 真实抖音环境验证 |
| 复制降级 | 已可用 | 增加更清晰的图文引导 |
| 订单号说明 | 已展示“不上报后端” | 后续需与 Agiso/订单系统联调确认字段含义 |

## 十、建议的正式修复验收标准

为了避免“修了但没验”的问题，我建议 Claude 完成上述修复后，至少按以下标准验收。验收应覆盖浏览器点击、接口返回、错误提示和非技术人员理解成本。

| 验收项 | 通过标准 |
|---|---|
| 新增选手 | 在后台输入姓名与不重复序号后点击按钮，成功新增，无 JSON parse 报错 |

| 新增队伍 | 输入队名后点击按钮，成功新增，无 JSON parse 报错 |
| 表单回车 | 在任意基础数据输入框按 Enter 不触发根路径 POST 或页面刷新 |
| 非 JSON 响应 | 若代理/服务异常，前端提示“接口返回异常，请检查服务状态”，不暴露 `Unexpected token '<'` |
| 分队设置 | 操作员可通过姓名和队名完成设置，无需记 ID |

| 演示环境标识 | 临时演示环境顶部有明显 DEMO 标记 |

今晚内测的总体结论是：**系统主链路已经具备演示价值，但后台运营体验距离“非技术人员可独立操作”还有明显差距。** 对项目而言，这不是坏消息，因为问题暴露在内测阶段，而不是直播当天。下一步应优先修复“前端表单误提交导致 JSON 解析错误”和“分队与卧底设置依赖 ID”的两个问题，再进入小程序真机、Agiso 与 C16 的后续联调。

> 最后提醒：本报告中的临时修复发生在隔离演示工作区，不等于已经进入主仓库正式代码。建议 Claude 审阅后，将 P0/P1 项按正式开发流程落到主仓库，并补充对应测试。
