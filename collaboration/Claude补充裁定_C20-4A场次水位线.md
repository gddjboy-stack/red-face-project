# Claude 补充裁定：C20-4A 水位线必须按「场次」归零

日期：2026-07-31　致：Manus

## 新增事实（John 已查证）
抖音官方直播中控台**只提供本场直播的点赞/评论/礼物实时累计数，不提供跨场次历史累计总数**。即：**每场开播时，中控台上的三个数字都从 0 重新开始。**

## 对 C20-4A 的直接影响（必须处理，否则必然出错）
原设计中"当前总数 < 上次总数则提示运营确认"被当作**罕见异常**处理。基于新事实，**该情况在每一场新直播的首次录入时必然发生**：

> 例：8/3 收官时点赞水位线 = 50,000；8/9 开播后运营录入 3,000 → `3,000 − 50,000 = −47,000` → 人气倒扣四万七。

## 设计要求（两条，缺一不可）
1. **显式入口（主路径）**：录入面板增加「**新场次开始（清零水位线）**」按钮，运营开播时点击一次，三条来源水位线（gift / like_delta / comment_delta）同时归零，并记录清零时间与 operatorId 进 `operations_log`。
2. **自动兜底（防漏点）**：提交时若「当前总数 < 上次水位线」，**不得写入负值**，须弹窗提示：「检测到数值小于上次记录，是否为新场次开始？」——运营确认则按新场次处理（水位线归零后再计算本次差值），否则取消本次提交。

## 实现说明
- **不需要新建完整的「场次」实体**。水位线本身可重置即可满足需求，避免引入新的数据模型与关联关系。
- 轮次（round）与场次不是一回事：8/3 与 8/9 属同一轮次的两场直播，因此**不可用 roundId 作为水位线的重置依据**。
- 断流重连导致中控台重新计数的情况，由第 2 条自动兜底覆盖。

## 验收要点
- 模拟"上场水位线 50,000 → 新场次录入 3,000"，验证不产生负值、且按新场次正确计为 +3,000
- 清零操作有审计留痕
- 群投票水位线不受影响（其数据源为我方独立账本，天然跨场累计，**不需要归零**）
