## 一、结论先行

John 的观察是准确的，界面上确实没有这两处。但这不是 Claude 凭空编写手册，也不是界面加载失败，而是一个明确的**前后端进度落差**。

| 层次 | 校准中控台读数 | 直播人气录入（填累计总数） |
| --- | --- | --- |
| 数据库表 | 已建（`live_metric_watermark`） | 同上 |
| 后端接口 | 已实现，实测返回 200 | 已实现，实测返回 200 |
| 后端提示文案 | 已实现，与手册措辞一致 | 已实现 |
| 单元测试 | 已有三个测试类 | 同上 |
| **前端界面** | **完全未实现** | **完全未实现** |

也就是说，这两个功能在系统里是「做完了但没有门」的状态：能力都在后端，运营点不到。

## 二、后端确实存在，且文案与手册对得上

在 `AdminControlController.java` 中共有六个相关端点，我逐个实测确认可用。

| 源码行 | 方法与路径 | 用途 | 实测 |
| --- | --- | --- | --- |
| 133 | GET `/api/admin/live/watermarks` | 查三项读数基准 | 200 |
| 145 | GET `/api/admin/live/watermarks/calibrate-copy` | 取校准与撤销的提示文案 | 200 |
| 157 | GET `/api/admin/live/metric-entry/preview` | 增量预览 | 200 |
| 169 | POST `/api/admin/live/metric-entry` | 提交累计读数 | 已验证存在 |
| 187 | POST `/api/admin/live/watermarks/calibrate` | 校准（即「开始新一场」） | 已验证存在 |
| 198 | POST `/api/admin/live/watermarks/revoke-calibration` | 撤销校准 | 已验证存在 |

支撑类为 `LiveWatermarkService`、`LiveMetricEntryService`、`LiveMetricWatermark`、`LiveMetricWatermarkMapper`；测试类为 `LiveWatermarkC20Test`、`CalibrationCopyC20Test`、`LedgerSessionTagRegressionC20Test`；建表语句位于 `schema-h2.sql` 第 337 行与 `db/db_schema.sql`。

尤其值得注意的是 `calibrate-copy` 返回的文案，它与手册的措辞几乎逐字对应：

> **按钮文字**：开始新一场直播（校准中控台读数）
> **确认弹窗**：此操作只重置中控台读数基准，不会改变任何选手的人气值。确认开始新一场直播的计数吗？
> **成功提示**：读数基准已校准，请从中控台读取当前数字录入。本次操作未改变任何选手的人气值。
> **撤销提示**：上一次校准已撤销，读数基准已恢复。本次操作未改变任何选手的人气值。

手册第二节写「这个操作不会改变任何选手的人气值，只是告诉系统中控台的数字重新从 0 开始了。系统会在确认弹窗里再说明一次」——这句话与上述文案完全吻合。**Claude 是照着后端已实现的能力写的手册，写得没错，只是写早了。**

我也实测了增量预览的行为，证明「填累计、系统算差值」的设计确实成立：

```
GET /api/admin/live/metric-entry/preview?metricType=gift&currentTotal=3000
→ {"metricType":"gift","currentTotal":3000,"lastTotal":0,"delta":3000,
   "sessionSeq":"20260802-075651-5891","needsCalibration":false,"message":"本次增量 3000"}
```

## 四、最需要警惕的一点：「模拟注入」会被运营误当成正式录入入口

这是本次核查中我认为风险最高的发现，请 Vincent 和 Claude 一并留意。

「模拟注入」区的事件类型下拉选项是「礼物 gift / 点赞 like_delta / 留言 comment_delta」，与 `metric-entry` 接口的三个 `metricType` 完全一致。一个照着手册第三节操作的运营，在场控操作页找不到「直播数据录入」区，却会看到一个同样有礼物、点赞、留言三选项、同样有数值输入框的区块，**他极可能认定这就是手册说的那个入口**。

但两者的录入范式正好相反：

| 维度 | 模拟注入（界面现有） | metric-entry（手册描述） |
| --- | --- | --- |
| 填什么 | 本次**增量** | 中控台**当前累计总数** |
| 谁算差值 | 运营自己算 | 系统用水位线算 |
| 设计用途 | 开发调试 | 运营现场录入 |
| 是否有基准保护 | 无 | 有，跨场需校准 |

后果是可以推演出来的。假设中控台点赞累计到 3000，运营照手册「直接填当前看到的总数」，在模拟注入里填了 3000。系统按增量处理，直接注入 3000。五分钟后中控台涨到 3500，运营再填 3500，系统又注入 3500。两次实际增量应为 3000 与 500，最终却注入了 6500，**多计了 3000**。而且这个错误随每次录入不断放大，越到后面偏差越大。

手册第三节明确写着「不用自己算差值，系统会算」，这句话在当前界面下是**危险的**——因为唯一看起来像那个入口的区块，恰恰是必须自己算差值的那一个。

这是我建议把「模拟注入」区在运营可见界面中隐藏或改名的原因，理由不是它有 bug，而是它与一个尚未上线的功能长得太像。

## 五、附带发现：培训环境曾整库丢失，已修复

核查过程中我发现培训环境在 07:50 之后所有接口返回 500，报错为 `Table "xxx" not found (this database is empty)`。经查这不是部分表缺失，而是 26 张表全部消失。

根因是 H2 内存库连接串 `jdbc:h2:mem:redface` 缺少 `DB_CLOSE_DELAY=-1` 参数。H2 内存库的生命周期绑定在连接上，当 Hikari 连接池把空闲连接全部回收后，最后一个连接关闭的瞬间整个库被销毁。培训环境从 06:36 最后一次成功请求到 07:50 之间约 74 分钟无人访问，连接池清空，库随之消失。而 Java 进程本身仍存活，`spring.sql.init` 不会重跑，所以库空了且不会自愈。

这个问题**只影响用 H2 的临时培训环境，不影响生产**，生产用的是 MySQL。我已在 `application-test.yml` 中补上 `DB_CLOSE_DELAY=-1`，重启后端确认 26 张表全部重建，并重新灌入演示数据（两支队伍、六名选手、一个轮次、十二条商品原价、一笔销量记录）。环境目前恢复可用。

需要向 John 说明的是，**此前拍摄的 17 张截图所依赖的数据已随该次丢失而消失**，截图本身有效，但若要在环境里复现同样的画面，需按恢复后的数据重新操作。

## 六、需要 John 决策的两件事

第一件是**手册的处理方式**。手册第二、三节描述的功能界面不存在，若原样发给运营，他们会在现场找不到入口，进而可能误用模拟注入造成人气重复计数。摆在面前的是两个方向：要么把前端接入排进 8/9 首场之前，要么把手册这两节暂时标注为「功能待上线」并给出替代流程。这涉及排期与人力，属你的管控范围。我倾向于前者，因为替代流程本身就需要运营手工算差值，出错概率比接一个前端界面更高。

第二件是**培训材料要不要一并调整**。我此前交付的《兼职培训材料_销量录入_V1.0》只覆盖销量录入，明确写了「其余页签一律不点」，因此不受本次差异影响。但如果 Vincent 计划让兼职人员也承担直播读数录入，那份材料需要扩写，且必须等前端上线后才能拍截图。

## 七、需要 Claude 回应的三个问题

第一，`metricType` 的取值是 `gift`、`like_delta`、`comment_delta`，后两个带 `_delta` 后缀，但接口语义是「传入当前累计总数、由服务端算差值」。命名与语义相反，容易让后续接入前端的人误传增量。这是历史遗留还是有意为之？是否需要更名或至少在接口文档中加注。

第二，前端接入这六个端点是否已在排期内。手册 v1.0 按已实现口径书写，若排期在 8/9 之后，手册需要先行标注。

第三，是否同意把「模拟注入」区对运营隐藏（例如与订单导入一样改为 `?experimental=1` 才显示）。它是调试功能，却与即将上线的正式录入入口外观高度相似，误用后果是人气重复计数且难以察觉。
