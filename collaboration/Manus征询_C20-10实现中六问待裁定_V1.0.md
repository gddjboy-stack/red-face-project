## 一、Q1｜schema 生成器脚本已腐坏，跑一次即回退测试环境（建议登记缺陷）

你在裁定中将两份 schema 的同步定为 DEBT-002，要求手工同步并在交付时列行号供核对，并写明「重启信号是再发生一次不同步故障」。这条裁定成立，但仓库里还有一件与之直接相关、且比不同步本身更危险的东西。

`backend/redface-backend/scripts_generate_schema_h2.py` 是一个以生产 MySQL 脚本为唯一源头、自动生成 H2 脚本的转换器。我最初以为它意味着「靠人工同步」这个前提不成立，于是实测跑了一遍并与现役 H2 脚本比对。结论是它**已经与现役脚本分叉，现在执行一次就是回退**：

| 差异 | 后果 |
| --- | --- |
| 丢掉开头 27 行 `DROP TABLE IF EXISTS` | 现役脚本第 1 行注释写明：H2 测试库会因不同 Spring 测试上下文重复初始化，必须先按外键反向顺序清表。丢掉后跑多个测试类会撞「表已存在」 |
| 把 `TIMESTAMP NOT NULL` 改回带 `DEFAULT CURRENT_TIMESTAMP` | 现役脚本对 `start_time`/`end_time`/`occurred_at`/`expires_at` 刻意去掉了默认值，生成器会加回来 |
| 剥离所有注释 | 生成器用 `re.sub` 清 `COMMENT`，连 `--` 行注释一并受影响，会擦掉 C20-4B 的事故记录与 C20-4B/C20-6 的设计说明 |

**危险点不在于它有 bug，而在于它的文件名完全可信。** 下一个接手的人（包括下一轮的我）看到「generate_schema_h2」这个名字，会理直气壮地拿它来同步 schema，然后静默破坏测试环境——而测试环境被破坏的表现是「表已存在」这类看起来像环境问题的报错，不会有人立刻联想到是脚本干的。

这与我在 C20-9 撞过的坑同类：文件看起来是源码，实际是产物；或者反过来，工具看起来能用，实际已经腐坏。

**请裁定处置方式**，我倾向第三项但成本最低的是第一项：

1. 删除该脚本，彻底消除误用可能
2. 修复它使其可用（补 DROP 段、保留注释、对齐类型转换），让 DEBT-002 自动化
3. 保留但在文件头部加显著失效警告，并在文件名上体现（如改为 `DEPRECATED_generate_schema_h2.py`）

我已将 H2 脚本恢复为手工修改版本，当前 `SchemaParityC20Test` 通过（Tests run: 1, Failures: 0）。

## 二、Q2｜团队人气存在两处不一致，且团队均分按裸值分配（既有缺陷，非本卡引入）

我在开工前反对意见中提出「同一选手在卧底榜与场控监控显示两个数」，并据此要求把消费点落成可数的两处。实现过程中我发现，**这个问题在团队维度上已经真实发生了，而且比卧底维度严重**。

团队系数的折算写在 `C9QueryMapper.findTeamBoard` 那条 SQL 里；但 `StatsMapper.findTeamPopularity` 是另一条语句，**没有折算，返回裸值**。三个地方消费后者：

| 消费点 | 位置 | 后果 |
| --- | --- | --- |
| 场控监控 `teamPopularity` | `LiveHomeService:111` | 与团队榜显示数不一致 |
| 团队模式目标人气 | `LiveHomeService:117`、`119` | 同上 |
| **团队人气均分的分配总量** | `TeamDistributionService:70` | **按裸值分配，分出去的人气总量与团队榜显示的数字不符** |

第三项是我认为最严重的：均分是一次性写账本的动作，一旦按裸值分完，事后无法通过「重新读一次」纠正。假设团队系数为 ×0.8、团队池裸值 100 万，团队榜显示 80 万，而均分实际会把 100 万分给成员——多分出 20 万人气，且账本上每一笔都合法，没有任何告警。

**我没有在本卡修它**，理由是：团队系数折算范围超出 C20-10 授权，改动触及结算与团队分配链路，需要独立的回归验证。请裁定是否单独立卡，以及是否需要在 8/9 之前完成（若 8/9 会用到团队人气均分，则必须前置）。

## 三、Q3｜`spy_status` 字段已存在但从未被写入，识破标记应否写它

`player_round` 表里有一个字段：

> `spy_status VARCHAR(20) NULL COMMENT 'hidden/revealed/exposed(被识破)'`

我全代码库搜索了 `spy_status` 与 `spyStatus`，结果是：**只有一处测试断言它不出现在用户侧响应里，没有任何写入代码**。也就是说这个字段自建表起就是空的，`exposed(被识破)` 这个语义从未落地过。

C20-10 要引入「识破标记」，于是出现三种可能，请裁定：

| 方案 | 做法 | 风险 |
| --- | --- | --- |
| A | 只记账本 `factor_type='exposed_halve'`，不动 `spy_status` | `spy_status` 永久空置成僵尸字段，下一个人仍会被它误导 |
| B | 只写 `spy_status='exposed'`，系数减半由它派生 | 账本失去独立性，撤销减半时需回改状态字段 |
| C | 两处都写 | 双写不一致风险：撤销账本时若漏改 `spy_status`，两者矛盾且无人察觉 |

我倾向 **A + 明确处置 `spy_status`**：账本是唯一真相来源，同时请裁定 `spy_status` 是删除（若确认无用）还是补注释说明「由账本派生，不直接写入」。留一个语义诱人却永久为空的字段，与 Q1 的腐坏脚本是同一类问题。

另外需要提示：既有的 C13 真相识破功能（`SuspicionService`）是**用户侧投票猜卧底**，它只统计候选分布，不判定卧底是否真被识破。C20-10 的「识破」是**运营侧根据现场结果施加系数**。两者名字相近但机制无关，请确认我的理解正确，避免我把系数减半错接到 C13 的投票结果上。

## 四、Q4｜识破减半是否允许重复施加，撤销后能否重新施加

我已在 `SpyCoefficientLedgerMapper` 中提供 `countActiveByType`，可用于阻断同类型重复施加。但是否启用需要你裁定，因为这取决于玩法而非技术：

若允许重复施加，同一选手同一轮被减半两次会得到 ×0.25。以基础卧底人气 205,000 计，第一次减半后 102,500，第二次后 51,250。**两次操作都会成功、都会记账，运营看到的只是数字变小，不会有任何提示告诉他「已经减过一次了」。**

请裁定两问：

1. 同一选手同一轮的 `exposed_halve` 是否只允许一次？（我倾向阻断，并在拒绝消息中带上已施加时间与操作人）
2. 若已撤销，是否允许重新施加？（我倾向允许，否则误操作撤销后无法补救）

`task_bonus`（任务加成）我理解为可多次施加，因为一场直播可能完成多个任务，请确认。

## 五、Q5｜参与人数校验放在哪一侧

卡片要求「参与人数小于任一选手得票数时阻断」。实现时发现录入顺序不确定：运营可能先录参与人数再录票数，也可能反过来。因此单侧校验会漏：

| 只在录参与人数时校验 | 只在录票数时校验 |
| --- | --- |
| 先录参与人数 100、后录票数 150 → 不拦 | 先录票数 150、后录参与人数 100 → 不拦 |

我计划**两侧都校验**：录参与人数时比对该轮已录的最高票数，录票数时比对已录的参与人数（为 NULL 则跳过）。代价是每次录入多一次查询。

请裁定是否同意，以及**已经录错之后如何处置**：若参与人数已存为 100、票数已存为 150（历史数据或跨版本产生），系统应当在读取时报警，还是允许运营强制覆盖参与人数？这一问关系到 8/9 当晚出错后能否自救。
