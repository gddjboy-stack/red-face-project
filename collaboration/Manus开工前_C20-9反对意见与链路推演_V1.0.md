## 二、反对意见一：礼物一行按你的设计必然报错（阻塞，必须先裁定）

你在 B.5 要求「顶部当前场控目标下拉，**可随时切换、无固定顺序**」，同时 B.2 要求三行（点赞/评论/礼物）**一次提交**。这两条在后端实现下不能同时成立。

`LiveMetricEntryService` 第 125-142 行：

```java
if (LiveWatermarkService.METRIC_GIFT.equals(preview.metricType())) {
    req.setTargetType(TARGET_PLAYER);
    req.setTargetId(requireCollectPlayerId());   // ← 这里
}

private int requireCollectPlayerId() {
    CollectState current = collectStateService.getCurrent();
    if (current != null && TARGET_PLAYER.equals(current.getMode()) && current.getTargetId() != null) {
        return current.getTargetId();
    }
    throw new IllegalStateException("礼物按总数录入需要当前场控为 player 模式并已指定目标选手");
}
```

**礼物录入强制要求当前场控 `mode=player` 且已指定目标选手。** 而点赞/评论走 `PopularityService.resolveTarget()`，`mode` 为 player/team/pool/spy 四种都能正常归属。

于是：运营把场控切到「团队 team」或「总池 pool」（这两个模式在集赞目标切换卡里是正常选项，现场也确实会用），然后在录入区填三行提交——**点赞、评论成功入账，礼物这一行报 500 系错误**。三行是一次提交，运营看到的会是「提交失败」，但实际上两行已经写进账本了。他大概率会改数再提交一次，于是点赞和评论被重复计入。

这正是这张卡要消灭的那类问题，只是换了个位置。

**我的建议（请裁定选一）**：

方案甲，礼物一行按当前场控模式动态禁用。`mode!==player` 时礼物输入框置灰，旁边给一行灰字说明「礼物按总数录入需当前场控为选手模式」。这最贴近后端现状，改动最小，但运营会问「为什么礼物不能填」。

方案乙，三行改为**逐行独立提交**，每行一个提交按钮，各自成功各自失败。这样礼物失败不会牵连点赞评论，但违背你 B.4「一次提交三项」，且运营要点三次。

方案丙，仍一次提交，但前端**先预检**：若 `mode!==player` 且礼物行有值，提交前弹窗「当前场控为团队模式，礼物无法按总数入账，是否仅提交点赞与评论？」由人确认后只提交两行。

**我倾向方案丙叠加方案甲的提示文字**，理由是它既不让运营做心算、也不静默丢数据，且把选择权交给现场的人。但这三条都是产品决策，不是我该定的。

## 三、反对意见二：卡里说的「乐观锁参数」后端不存在（阻塞，需确认）

你在 B.4 写「按后端签名传乐观锁参数」。我核了 `AdminRequests.LiveMetricEntryRequest`（第 140-156 行），字段只有五个：

| 字段 | 类型 |
| --- | --- |
| `metricType` | String |
| `currentTotal` | Long |
| `operatorId` | String |
| `reason` | String |
| `idempotencyKey` | String |

**没有版本号、没有 expectedSeq、没有任何乐观锁字段。** 并发保护实际是靠 `idempotencyKey` 的唯一索引（`PopularityService` 第 66-69 行捕获 `DuplicateKeyException` 返回 `duplicated`），是幂等而非乐观锁。

两者行为差别很大：幂等键只能拦「同一个键重复提交」，拦不住「两个运营各自读到同一个水位线、各填不同数字先后提交」——后者两次都会成功，第二次的增量按第一次更新后的水位线算，结果偏小且无人察觉。

**请确认是哪一种情况**：一是你笔误，实际意思就是幂等键，那我按幂等键实现（每次表单变更重新生成 key，防连点）；二是你确实要乐观锁，那需要后端加字段，**这属于后端改动，按你本卡「代码一律由 Manus 实现」的新规矩我可以做，但要你先确认加在哪一层、以及 8/3 前是否值得动数据库**。

我倾向第一种。8/3 只有一个运营在录，双人并发不是当前场景，为此改后端不值得。

## 五、反对意见四：http.ts 会吞掉 40910 的 preview，必须先改造

这条不需要你裁定，是我必须做的前置改动，报备一句以免你验收时以为我越界改了公共层。

`src/api/http.ts` 现在这样写：

```typescript
if (!response.ok || payload.code !== 0) {
  throw new Error(payload.message || `请求失败：${response.status}`)
}
```

`payload.data` 被整个丢掉。而 40910 的 EntryPreview 恰好在 `data` 里，前端拿不到 `lastTotal` 与 `currentTotal`，就没法在校准确认弹窗里展示「当前 3000 小于上次 50000」这种关键对照。

我会给 `http.ts` 加一个携带 `code` 与 `data` 的错误类型（不改现有调用方行为，只在错误对象上多挂两个属性），使 40910 与 40920（订单导入硬阻断）都能拿到 payload。这是**公共层改动**，会影响所有页面的错误路径，所以我单独说明。

## 六、链路推演（每行主语是人，按纪律第三条）

以下是接入完成后 8/3 现场的完整链路。我把每一步的操作人写在句首。

**开播前十分钟。** 场控（Vincent 指定的现场人员）打开后台「场控操作」页，看到页面顶部一个醒目按钮，文案由后端下发，写着「开始新一场直播（校准中控台读数）」。场控点它，弹出二次确认，里面有后端下发的那句「此操作只重置中控台读数基准，不会改变任何选手的人气值。确认开始新一场直播的计数吗？」。场控点确认，页面提示校准成功，同时三行录入区的「上次总数」全部变为 0。

**若场控点错了。** 场控立刻点旁边的「撤销校准」。若此时还没录过任何数据，页面提示撤销成功、三行「上次总数」恢复原值。若已经录过，后端拒绝并返回归零前的原值，**前端把这个错误连同原值一起显示出来，不吞**，场控据此知道要找人工核算。

**开播后每三到五分钟。** 场控切到浏览器另一个标签页看抖音中控台，读到点赞 12000、评论 800、音浪 3500。场控回到后台，在三行里分别填 12000、800、3500。场控填的过程中，每行下方实时显示后端算出的增量与折算人气，例如点赞行显示「上次 9000，本次增量 3000」。场控确认三个增量都不离谱，点提交。

**若场控填的数比上次小。** 场控可能在新一场开播后忘了校准，直接填了 3000（而上次记录是 50000）。场控点提交，后端返回 409/40910、**一个字都没写进账本**，前端弹出确认框，展示后端那句「检测到当前总数 3000 小于上次记录 50000，通常说明中控台已重新计数（新场次开播或断流重连）。是否按新一场直播处理？校准只重置读数基准，不会改变任何选手的人气值。」场控点「是」则先校准再录入，点「否」则回去核对自己是否读错了行。

**若场控要换归属对象。** 场控在集赞目标切换卡里把目标从 1 号选手改到 2 号。场控点确认前，前端先检查礼物水位线：若本场一次都没录过、或距上次录入已超过三分钟，弹窗提示「本场尚未录入过礼物数据。若切换前已有礼物进入，请先录入一次再切换，否则这段礼物会整段归到下一位选手头上。」场控可以选择先去录一次再回来切。

**大屏侧。** 导播在 OBS 里加浏览器源指向大屏页。**页面加载时先探活，Cookie 在有效期内就直接进榜面，不再弹令牌闸门**，导播不需要在开播前手输令牌。导播点页面上的「全屏」按钮进入全屏，版式自动重算。榜面每三秒刷新，每六秒自动翻屏，**12 人两屏会真正轮到第二屏**，第 11、12 名的选手能被观众看到。导播若用鼠标拖动榜面查看，自动滚动暂停二十秒，不会在他眼前跑掉。

**运营看不到的东西。** 「模拟注入」区在加了 `?experimental=1` 之后才出现，场控的日常地址里没有这个参数，所以他不会看到那个与正式录入外观相似的下拉框，也就不会把累计总数填进按增量处理的入口。
