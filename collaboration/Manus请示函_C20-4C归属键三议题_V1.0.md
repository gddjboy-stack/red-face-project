## 一、议题一：`players.display_code` 没有任何写入入口

### 1.1 事实与证据

整个订单归属链路是「抖店订单表的商家编码 → `players.display_code` → `player_id` → 人气值」。这条链路的中间环节，在生产环境**无法被写入**。

证据一，插入语句不含该列。`BasicDataMapper.insertPlayer` 的 SQL 为：

```java
@Insert("""
        INSERT INTO players (name, number, status)
        VALUES (#{name}, #{number}, #{status})
        """)
```

证据二，不存在任何更新语句。`grep -rn "UPDATE players" src/` 在全项目返回空。

证据三，请求 DTO 有字段但从未被使用。`BasicDataRequests.CreatePlayerRequest` 定义了 `private String displayCode;` 及其 getter/setter，但没有任何 SQL 引用 `#{displayCode}`。这是最容易误判的一点：**从 DTO 看功能像是存在的**。

证据四，查询语句也不返回该列。`BasicDataMapper.findPlayers` 的 SELECT 列表为 `player_id, name, number, status, created_at, updated_at`，没有 `display_code`。因此即使某天该列被写入，场控后台的选手列表也看不到它。

证据五，实测确认字段被静默丢弃。我向运行中的后端发起真实请求：

```
POST /api/admin/players  {"name":"林一","displayCode":"P01","number":1,...}
→ 200 {"playerId":1,"name":"林一","number":1,"displayCode":null,...}
```

接口返回成功，`displayCode` 为 `null`。**没有报错、没有校验、没有告警**。

### 1.2 为什么 196 项测试全绿也没能发现

因为所有相关测试都绕过了生产环境唯一的入口。`OrderImportC20Test`（第 65、69 行）与我新写的 `OrderImportBlockC20Test`（第 69、73 行）都是直接执行：

```sql
INSERT INTO players (player_id, name, number, display_code, status) ...
```

测试用 JDBC 直接造数据，从不调用 `POST /api/admin/players`。所以测试验证的是「假如 `display_code` 有值，归属逻辑正确」，而没有验证「`display_code` 能否被填上」。

这与你在 C20-4B 对照表第 72 至 78 行记录的缺陷是**同一类**，且更隐蔽。当时的问题是「两份 schema 不同步，测试全绿无法发现」，你的修复是新增 `SchemaParityC20Test` 把隐式假设变成显式断言。这次的问题是「列存在于两份 schema，但没有代码路径能写它」——`SchemaParityC20Test` 只比对 DDL 文本，对此无能为力。

我认为这暴露了一个比单个 bug 更值得记录的模式：**当某一列只被测试的 setup 代码写入、而从不被生产代码写入时，测试覆盖率越高，越容易掩盖入口缺失。**

### 1.3 与 C20-4B 待确认事项 A-2 的关系

你在 C20-4B 对照表第 91 行列了待确认事项 A-2：

> 商家编码必须与选手编号一致（`players.display_code`），上架时即约定 —— 负责人 John / 彬少，时限 8/7

第 96 行还标注：

> A-1 与 A-2 是**硬阻塞**：商家编码若与选手编号不一致，或某商品漏录单价，该商品的订单将全部判为未归属、不计入人气。

**A-2 被表述为一项「人类需要去约定的事」，但它同时也是一项「系统需要提供入口的事」，后者没有被记录为任何一张卡的交付物。** 即便 John 与彬少在 8/7 完美地约定了编码规则，运营届时仍然无处录入。这是我判断它属于遗漏而非有意省略的主要依据。

### 1.4 现场后果推演

运营在场控后台建完 12 位选手，`display_code` 全部为 `NULL`。导入订单表时，每一行的商家编码都查不到对应选手，全部判为 `unattributed`。我本次实现的硬阻断会把整批拦下并给出明确提示。

**阻断本身是正确的**——它精确地做了它该做的事。但运营在界面上找不到任何地方能配 `display_code`，会彻底卡死，除非有人临时连生产数据库执行 UPDATE。在直播现场做这件事的风险不需要我展开。

需要指出的是，如果没有 C20-4C 的硬阻断，这个缺陷的表现会是「导入成功、全场选手人气值为零、无人察觉异常」。**硬阻断把一次静默的结算灾难，变成了一次显性的操作卡死。** 这是阻断机制第一次发挥作用，也印证了它的价值。

### 1.5 三种可能性与我的倾向

| 可能性 | 支持证据 | 反对证据 |
| --- | --- | --- |
| 甲：由 C20-4A/4B 提供，那两张卡漏做 | `display_code` 是 C20-4B 期间补进 H2 schema 的 | C20-4B 对照表未把「写入入口」列为交付物 |
| 乙：原设计用 `number` 做归属键，`display_code` 是冗余 | `number` 已有唯一约束且可写入 | `OrderSalesLedgerMapper` 明确按 `display_code` 查；该列有独立唯一约束 `uq_display_code`；DDL 注释写明「与 players.display_code 对应」 |
| 丙：入口被整体漏掉，需在 C20-4C 补上 | 上述五条证据；DTO 有字段却无 SQL 引用，符合「写了一半」的特征 | 超出 C20-4C 卡片范围 |

我倾向**丙**。理由是乙可以被直接排除：`db_schema.sql` 第 336 行的注释写明「商家编码,即选手编号如P12(与players.display_code对应)」，且 `uq_display_code` 是独立唯一约束——冗余字段不会被加唯一约束，也不会被 Mapper 当作查询键。甲与丙的区别只在于「记在谁的账上」，对现场无影响，但对项目管理有意义，这一点请你判断。

### 1.6 我建议的修复方案（待批准后执行）

| 改动 | 文件 | 说明 |
| --- | --- | --- |
| 插入语句补列 | `BasicDataMapper.insertPlayer` | 加入 `display_code`，允许建选手时直接指定 |
| 查询语句补列 | `BasicDataMapper.findPlayers` / `findPlayerById` | 否则前端无法显示与核对 |
| 新增更新入口 | `BasicDataMapper` + `BasicDataService` + `BasicDataController` | `PUT /api/admin/players/{playerId}/display-code`，供已建选手补配 |
| 唯一冲突处理 | `BasicDataService` | `uq_display_code` 冲突须返回明确业务错误，不可让 500 裸奔到前端 |
| 前端可编辑列 | `App.vue` 基础数据 tab | 选手列表增加「商家编码」列，可就地编辑 |
| 空值告警 | 订单导入页 | 存在 `display_code` 为空的在场选手时，页面顶部常驻告警 |

最后一项是我主动加的，请一并裁定是否保留。理由：`display_code` 为空不会在导入前暴露，只在导入时以「全部未归属」的形式爆发。**在运营尚有时间处理的时刻提示他，比在阻断时告诉他更有价值。**

我另外建议一项**测试纪律**：新增一个测试，走 `POST /api/admin/players` 真实接口建选手，然后断言 `display_code` 已落库并能被 `findPlayerNameByDisplayCode` 查到。这样能防止同类「入口缺失但测试全绿」再次发生。这类测试与 `SchemaParityC20Test` 互补——后者管「列是否存在」，前者管「列是否可写」。

## 二、议题二：每选手多商品编码，使按选手汇总口径失效

### 2.1 John 的业务前提

我今天向 John 确认商家编码的填写方式，答复原文：

> 抖店订单表里的「商家编码」，运营是打算怎么填的？——**是每位选手每款商品一个独立编码。**

即 P01-CARD、P01-PHOTO 这样的形式，一位选手对应多个编码。

### 2.2 这与现有实现的冲突

`product_price_config` 的主键是 `merchant_code`（`db_schema.sql` 第 343 行），即「一个编码 → 一个单价」。这个结构本身**支持**多商品，无需改动。

但 C20-4C 卡片第 4 条要求：

> **按选手汇总核对视图**：每位**选手**本次将入账的件数与人气值合计

我实现的 `PlayerOrderSummary` 是**按商家编码分组**的。在多商品前提下，P01-CARD 与 P01-PHOTO 会成为两行。运营想核对「林一这场一共多少人气」，必须自己把两行相加。**卡片要求的「每位选手合计」，我没有给出。** 这是一个实质偏差，不是笔误，我不为它辩解。

### 2.3 更严重的问题：「件数」在多商品下失去判读价值

我把件数与人气值并列展示，唯一理由是：人气值偏高时，看件数就能判断这是「真的卖得多」还是「单价配错了」。这是卡片第 4 条所说的「第二道防线」的实际工作机制。

多商品情形下这个机制失效了。明信片卖 30 件、写真卖 5 件，合计「35 件」这个数字没有业务含义——因为两款商品单价不同，35 件对应的合理人气值区间是一个很宽的范围。**运营无法用它反推单价是否配错。** 换言之，在 John 给出的业务前提下，我实现的第二道防线是名存实亡的。

### 2.4 三个可选口径

| 方案 | 视图形态 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A：仅按选手汇总 | 一位选手一行，件数为跨商品之和 | 符合卡片字面要求 | 件数失去判读价值，第二道防线失效 |
| B：仅按编码汇总（现状） | 一个编码一行 | 件数与单价一一对应，可判读 | 给不出「每位选手合计」，需人工相加 |
| C：两级展开 | 选手为主行（含人气合计），可展开为各商品子行（含件数与单价） | 兼顾合计与可判读性 | 前端工作量增加，约需半天 |

我倾向 **C**。理由是 A 与 B 各自丢掉了卡片第 4 条的一半：A 丢掉了防线的有效性，B 丢掉了卡片明确要求的合计口径。而这道防线的存在意义恰恰在于「即使绕过阻断也能暴露异常」——一道失效的防线比没有防线更危险，因为它会带来虚假的安全感。

若你认为 8/3 前时间不允许做 C，我的次优选择是 B 加一行「本场合计人气值」的选手级小计，即在现有表格上加一层小计行而非完整的两级展开。这个折中约需一小时，能给出合计数字，但仍无法在选手层面判读单价异常。

### 2.5 一个附带问题

多商品编码还引出一个我没有实现、卡片也没提的场景：**同一位选手的某一款商品漏配单价，另一款配了。** 此时该选手会同时出现「有效行」和「未归属行」。硬阻断会拦下整批，这是对的。但「按选手汇总核对视图」里，这位选手的人气值是不完整的——它只统计了配价成功的那款商品。

如果运营选择显式排除（走覆盖入口），入账后该选手的人气值就是**偏低**的，且偏低的事实不会在任何地方显示，因为被排除的行人气值为 0，不进入汇总。我认为汇总视图应当为这种选手打上「本场存在被排除商品」的标记。这一点是否要做，请裁定。

## 三、议题三：未知订单状态是否纳入硬阻断

这是我在实施过程中两次提出、尚未获裁定的问题，在此正式提交。

### 3.1 现状

`OrderSheetParser` 遇到无法识别的订单状态（既非已知有效状态、也非已知无效状态）时，将该行判为 `invalid`，人气值为 0。我在 C20-4C 中新增了 `unknownOrderStatus` 标记与 `unknownStatusRows` 计数，并在预览页以告警形式列出具体状态名。

**但它没有被纳入硬阻断**，因为卡片第 2 条明确限定阻断范围为 `unattributed` 行的三种情形（未配置单价 / 编码无匹配选手 / 价格配置已停用）。我按原文实现，不擅自扩大。

### 3.2 我认为这是一个真实漏口

抖店若新增或改名订单状态（例如「平台介入中」这类），这些订单会被静默判为无效、不计人气，而阻断不触发。运营只会看到一条告警——**而告警是可以被忽略的，阻断不能。**

卡片第 3 条自己写明了阻断机制的原则：

> 原则：阻断防「无意识丢失」，不禁止「有意识排除」

未知订单状态导致的少算，性质上正是「无意识丢失」：运营不知道有这个状态、不知道它被算作无效、不知道少算了多少。按卡片自己确立的原则，它应当被阻断。我实现时把它排除在外，只是因为遵守卡片的字面范围界定。

### 3.3 反方论证（我作为蓝军对自己观点的攻击）

阻断的代价是现场卡死。如果抖店在 8/9 当天新增了一个无害的状态名（比如把「交易成功」改成「已完成」的同义变体），阻断会导致整批无法导入，而实际上那些订单可能本就该计入或本就该排除。**把判断权从运营手里拿走，在直播现场是有风险的。**

折中方案：未知状态**触发阻断，但可走同一个覆盖入口放行**，并在留痕中记录具体状态名。这样既不静默少算，也不至于卡死——运营看到具体状态名后可以当场判断。我倾向这个方案，但它意味着覆盖入口的语义要从「排除未归属订单」扩展为「排除系统无法判定的订单」，请你裁定这个语义扩展是否可接受。

四项超出卡片原文、需你确认的实现决定：

**第一，硬阻断不消费预览令牌。** 被拦时令牌仍有效。理由：阻断不是失败。若吞掉令牌，运营补完配置后想重新确认却发现令牌失效，容易误判成「已经导过一次了」——这个误判比原始漏配更危险。

**第二，覆盖必须逐笔全选，拒绝子集也拒绝超集。** 只勾一部分不予放行。若允许子集，运营勾 3 笔就放行 10 笔，未勾的 7 笔被无声排除，阻断等于失效。`OrderImportOverrideRequest` 中**故意不设「全选」布尔位**——布尔值能被前端默认勾上，逐笔子订单号无法在不看内容时凭空填写。

**第三，留痕先于入账。** 日志写失败则整次覆盖中止，宁可不入账。绝不允许出现「人气已加、没人知道谁放行的」。

**第四，`preflight` 独立实现而非复用 `preview`。** 两者只差「不生成令牌」，但这一差别是刚需：空跑后不能在系统里留一个亮着的确认入口。解析共用 `parseInternal`，避免「空跑通过、正式导入被拦」。

### 4.2 前端

前端形态最终**并入既有 `frontend/control-admin` Vue 工程**，而非我在 V3.3 中设想的独立单文件页面。改变理由：该工程已有构建部署链路，且 Admin 口令、401 处理、`operatorId` 均已封装，复用比新建更省时。此点与先前表述不一致，特此列出。

新增「订单导入」标签页，含商品原价配置、上传订单表（前置检查与上传预览两个入口）、预览汇总指标区、按选手汇总核对、未归属订单勾选排除、逐行明细（五类筛选）、确认入账、入账结果八个区块。`npx vue-tsc --noEmit` 无错，`pnpm build` 通过。

三个前端设计决定：换文件即作废旧预览，防「屏幕上是 A 文件的数字、手里是 B 文件的令牌」；前置检查结果在界面上自标识，防运营误判「已导入过」；普通确认按钮置灰仅为减少无效点击，真正的阻断在后端——前端置灰可被绕过，不作为保障。
