## 一、【阻塞】系数账本若照抄团队版的 delta 语义，加成与减半会变成相加

这是必须先裁定的一条，因为它决定表结构，改起来牵动全部后续实现。

任务卡第 52 行要求「新建 `spy_coefficient_ledger`（**镜像团队版结构**：player_id、round_id、**delta**、idempotency_key 唯一、operator_id、reason、created_at）」。我核了团队版的既有实现，`team_coefficient_ledger` 确实是 `delta INT NOT NULL`，而消费它的方法是：

> `statsMapper.incrementPlayerCoefficient(playerId, roundId, delta)`

也就是**增量累加**语义。但本卡第 68 行与第 86-90 行要求的是**相乘**：

> 卧底最终人气 = spy_popularity × 任务加成系数 × 识破减半系数

这两者在同一张表上不兼容。举本卡自己的例子（第 58 行「完成任务 ×1.3、又被识破 ×0.5」）：

| 语义 | 计算 | 最终系数 | 折算后（基础 205,000） |
| --- | --- | --- | --- |
| 卡里要的相乘 | 130 × 50 / 100 | **65**（×0.65） | 133,250 |
| 照抄 delta 累加 | 100 + 30 + (−50) | **80**（×0.80） | 164,000 |

差 30,750 人气。而且**两个数都不会报错**，界面上都显示得出来，运营无从判断哪个是对的。

更麻烦的是顺序。累加语义下先减半后加成、先加成后减半的结果相同（都是 80），所以 Vincent 答复里那句「第 1、2 问在数学上等价」在累加语义下**恰好也成立**，这会掩盖语义已经跑偏的事实——这是我认为最容易漏过去的地方。

**三个方案：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 账本存 `factor INT`（100 基数的乘数因子），`spy_coefficient` 由「所有 factor 连乘」推导 | 语义与公式一致；可追溯每一笔系数由谁施加 | 不镜像团队版，两套系数表结构不同 |
| B | 账本仍存 delta，但 `spy_coefficient` 用 `× factor / 100` 更新 | 表结构镜像团队版 | 字段名 delta 与实际乘法语义相反，是新的语义陷阱，日后必然有人误用 |
| C | 账本拆两列：`task_factor` 与 `expose_factor` 各存一项 | 直接满足卡第 91 行「分别显示两项来源」 | 若将来出现第三类系数需改表 |

**我倾向 A + C 的组合**：账本存 `factor` 与 `factor_type`（`task_bonus` / `exposed_halve`），`player_round_stats.spy_coefficient` 存连乘后的最终值。这样既满足「相乘」，又能靠 `factor_type` 分别回显两项来源，且新增第三类系数不必改表。

**明确反对方案 B。** 字段叫 `delta` 却做乘法，等同于给下一个接手的人埋一颗雷。C20-9 里已经出现过一次同类问题——`metricType` 叫 `like_delta` 而实际要传累计总数，Claude 当时的裁定是「历史遗留，不改」，但那是既有代码。**新建的表没有理由复制这个错误。**

## 三、`findSpyBoard` 的 SQL 别名不能动，否则前端静默变空

这条不需要裁定，是我要向你报备的实现约束，也请验收时核。

`PopularityBoardItem` 没有 `popularityValue` 字段，它靠一个额外 setter 接住 SQL 别名：

```java
public void setPopularityValue(long popularityValue) { this.value = popularityValue; }
```

前端表格绑的是 `prop="value"`。我改 `findSpyBoard` 加折算时，若顺手把别名改成 `spyValue` 之类，**编译通过、接口 200、表格人气列全空**。团队版 `findTeamBoard` 的折算写法可直接照抄：

```sql
CAST(COALESCE(trs.team_popularity, 0) * COALESCE(trs.coefficient, 100) / 100 AS SIGNED) AS popularityValue
```

我会保留 `AS popularityValue` 不变，并在改动处留注释说明原因。

## 五、参与人数存哪里，我需要一个明确裁定

| 方案 | 做法 | 说明 |

| A | `rounds` 表加字段 `voter_count INT NULL` | 最简单，但覆盖更新会丢历史，只能靠 `operations_log` 回溯 |

卡第 43 行要求「每次更新写 `operations_log`」，两种方案都能满足。**我倾向 A**——它是轮次的属性，天然属于 `rounds`；新建一张只有一个数值列的表，收益不足以抵偿多一张表的复杂度。但既然涉及生产表结构变更，请你裁定。

另外一处细节请确认：卡第 83 行要求「参与人数小于某选手得票数时**阻断**」。我要确认阻断发生在哪一侧——

## 八、一处方法论上的自我提醒

C20-9 我推演礼物冲突时漏了 `spy` 模式，原因是我只列举「哪些模式会失败」，没反问「哪个模式是主场景」。这次我改了做法：先查清消费点全集（grep 到 SQL 层，不看文档描述），再反推哪一处漏接会造成最难察觉的后果——于是发现了卡里漏列的场控监控这一处，以及卡里多列的大屏与导出两处。

**结论是：任务卡里的清单不能当作核查依据，只能当作核查起点。** 这一条对 Claude 验收我的实现同样适用。
